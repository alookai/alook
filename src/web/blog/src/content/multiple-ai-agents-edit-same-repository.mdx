Picture two coding agents opening the same repository. Agent A refactors `src/auth/middleware.ts`, while Agent B fixes a type error in that same file. Both open pull requests. Once the first PR merges, the second either hits a merge conflict or merges cleanly on top of assumptions that no longer hold.

**Git can flag overlapping lines, yet it cannot decide who should have owned the file.** You have to settle that before either agent starts editing.

Here are four failure patterns that show up across branches, working trees, and pull requests. [How to Bring Claude Code and Codex Into the Same Team](/blog/claude-code-and-codex-same-team) covers how separate runtimes work together as a team; this post looks one layer down at what happens on disk when both edit the same repo.

## Two agents edit the same file at the same time

Merge conflicts are the obvious outcome. The sneakier problem is a clean merge that breaks runtime behavior. Say Agent A tightens a validation helper to reject empty values, and Agent B adds a new caller that passes an empty default. Neither diff touches the other’s lines, so Git merges both without complaint, the build stays green, and the bug only shows up at runtime.

That happens when two task briefs both say "fix auth" without setting file boundaries, so each agent treats the whole module as fair game.

**Put allowed file paths directly in the task brief.** If Agent A owns `src/auth/` for this round, Agent B leaves those files alone until ownership changes. A short in-scope and out-of-scope path list does the job. A `CODEOWNERS`-style map also helps show who usually reviews a directory, though it won't lock files or assign live tasks for you.

Skip the heavy org chart. **One clear sentence naming which directories a task can touch is enough.**

## Both agents fix the same problem

You check your open PRs and find two fixes for the exact same lint error, or two separate versions of one small helper. One PR lands, and the other turns into wasted work.

Broad prompts like "fix type errors in the project" invite this right away. Left unbounded, coding agents tend to clean up every warning they spot, even work already assigned to another agent.

**Scope each task to named issues or paths.** "Fix the three type errors in issue #412" sets a clear boundary; "fix type errors across the codebase" guarantees overlap. When an agent spots useful cleanup outside its scope, log it as a separate task instead of bundling it into the current PR.

## Agents share uncommitted state

Agent A starts editing a file without committing yet. Agent B runs in the same checkout and reads A’s half-finished code, building on temporary edits, reformatting them, or overwriting part of the file. Git can tell you the working tree is dirty, without any way to show which uncommitted lines belong to which task.

The root cause is simple: multiple agents are sharing one branch or working directory at the same time.

**Give every task its own branch, and give concurrent tasks separate [Git worktrees](https://git-scm.com/docs/git-worktree).** Claude Code’s [`--worktree` / `-w`](https://docs.anthropic.com/en/docs/claude-code/cli-reference) flag starts an isolated worktree per task, and the same pattern works with any coding agent that runs in its own checkout.

Uncommitted edits shouldn't become another agent's baseline unless someone hands the checkout over on purpose. Each worktree gets its own directory and Git index while sharing repository history, so ignored files like dependencies, local `.env` files, and build output usually need their own setup. Watch out for test suites that share a localhost port or local database, too.

## The reviewer edits the author’s branch

A reviewer agent spots a bug, checks out the author’s branch, and pushes a fix straight to the PR. Now the branch mixes original implementation commits with review fixes, making the review trail much harder to follow.

This happens when "review" quietly turns into "edit until it looks right," because the prompt never said whether the reviewer should report issues or change code.

**Keep review feedback separate from code edits.** Have the reviewer leave PR comments, a short checklist, or suggested changes, and let the author apply the fixes. If the reviewer needs to take over the code, hand off ownership explicitly and put the new work in a separate commit or branch so the boundary stays visible.

Using different models or runtimes for author and reviewer works well when each role has a clear job and its own checkout. Either way, a human still approves what merges to main.

## What Git handles and what it cannot

![Hand-drawn comparison of what Git catches in multi-agent edits versus what still needs ownership rules](/blog/multiple-ai-agents-edit-same-repository/git-handles.webp)

| Problem | What Git catches | What Git does not know |
|---------|------------------|------------------------|
| Two agents change the same lines | A merge conflict to resolve | Who should have gone first |
| Behavior clash with no line overlap | Nothing; the merge succeeds | That the combined change is wrong |
| Two agents file the same fix | Nothing; both diffs look valid | That the work was already covered |
| Overlapping uncommitted edits | That the working tree is dirty | Which pending lines belong to which task |
| Review commits on the author branch | Who authored each commit | Which changes came from review |

**Git tracks file state and flags line collisions, while your team still needs rules for active ownership, merge order, and review.** Settle those rules before merging.

## How to review and merge changes from multiple AI coding agents

Suppose your schema, API, and UI branches all finish on the same afternoon, and each passes CI on its own. Merge them in the wrong order and those green checks won't save you: the API may still target the old schema, and the UI may call the old API.

1. Before coding starts, write down which behavior and files each branch owns, and park unrelated cleanup in another task. Give concurrent work its own branch and, when sharing a local clone, its own worktree.
2. Run CI on every pull request, keeping in mind that a green build only proves that branch passed on its current base commit, not alongside the other open branches.
3. Have the reviewer post findings while the author pushes fixes. If ownership changes hands, note the handoff and keep the new commits separate.
4. Merge dependencies first: schema, then API, then UI. For busy files, pick a single owner or sequence edits one task at a time.
5. After each merge, rebase the remaining open branches onto main and rerun tests that exercise the combined behavior. Keep a human on every merge approval.

Resolving line conflicts is the easy part. Catching stale assumptions across branches is harder, which is why rebasing and retesting after each merge matters.

## FAQ

**Can multiple AI agents safely edit the same repo?**  
Yes. Give each task scoped paths and its own branch. When tasks run at the same time, use separate worktrees, then review the combined result before merging.

**Do coding agents need separate machines?**  
No. Separate worktrees on the same machine give each task its own working directory. Dependencies, local env files, build output, ports, and databases may still need their own setup.

**Should a reviewer agent edit the author’s branch?**  
Usually no. The reviewer should leave comments or suggested changes. If it must take over the code, transfer ownership clearly and keep the new changes visible in a separate commit or branch.

**Does Alook handle git merges?**  
No. Alook coordinates which agent works on what. Git handles the merge. You approve what lands.
