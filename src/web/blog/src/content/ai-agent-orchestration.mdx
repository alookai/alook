**AI agent orchestration defines how agents receive work, exchange results, and decide what happens next.** In multi-agent orchestration, those rules connect several agents around a task: who owns each part, what evidence moves with it, and when work should stop or return to a person. Recovery still needs saved progress and a way to resume execution.

A customer reports that a signup button fails. One agent could investigate and prepare a fix; a separate reviewer might help. Before recruiting more agents, decide who will own the diagnosis and who will check the patch. Someone also needs to notice if either of them stops replying. A list of agent names will not settle those responsibilities.

## What is AI agent orchestration?

An agent can make several tool calls and revise its approach within one task. Orchestration concerns the rules around that work: assigning responsibility, making results available, recording progress, and deciding whether another step may begin.

## When multi-agent orchestration makes sense

**Keep one agent when it can finish the task with suitable tools and you can check the result.** Use ordinary code for deterministic work such as authentication and input validation. Neither check needs its own language model simply because it sits inside a larger process.

Splitting work becomes more useful when a task needs separate expertise, independent review, different permission scopes, or investigations that can proceed independently. Those benefits must justify the extra messages, latency, and failure points. Microsoft's [architecture guidance](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns) similarly recommends choosing the least complex arrangement that meets the requirements.

A concrete example appears in the [Hugging Face agents course](https://huggingface.co/learn/agents-course/en/unit2/smolagents/multi_agent_systems): a manager delegates web research to a specialized agent and uses the returned information. Study its implementation before adding a manager to your own task.

Before splitting the signup investigation, ask what another owner contributes. A reviewer with a separate remit can examine the patch against the reported failure. Creating four agents to run four predictable validation functions would add coordination without establishing a useful division of responsibility.

These methods can be combined. The investigator might choose which diagnostic tool to use, while a fixed rule prevents implementation until the problem is confirmed. A person can retain the decision to merge.

Sequential and parallel execution describe a different choice. A reviewer needs the patch before reviewing it; two independent investigations may run together. If they disagree, name who resolves the conflict. For a wider catalog, see [multi-agent workflow patterns](/blog/multi-agent-workflow-patterns).

## A bug report, from investigation to review

The following is a suggested workflow, not a measured test or a claim that a particular platform runs it automatically.

**Investigate the report.** Give the investigator the report, relevant environment details, and access to the necessary logs or code. Ask for reproduction steps and evidence that distinguishes a confirmed problem from a hypothesis. If the report cannot be reproduced, the owner should check the environment or logs and request the missing information. Patching waits until there is enough evidence to justify a change.

**Prepare a patch.** Once the problem is confirmed, hand the diagnosis to an implementation owner. The output should identify the patch version, checks actually run, results, and unresolved limitations. “Fixed” without a reference to the changed artifact leaves the reviewer guessing.

**Review that version.** The reviewer checks the patch against the evidence and acceptance criteria. A changed patch needs a matching review; an approval of an earlier version does not carry forward automatically.

**Request the human decision.** Present the reviewed patch and remaining risks to the person responsible for merging. A decision to revise returns work to its owner. Approval allows the next authorized action; a pending decision keeps the task paused.

Every transfer needs a small, explicit record:

- Task identifier, current owner, and named next recipient
- Relevant evidence and the exact artifact or revision
- Checks completed, results, and unresolved questions
- Access needed, completion criteria, and conditions that require a pause

Keep that record somewhere participants can retrieve it. A local path alone is insufficient if the recipient cannot access that machine. Share the necessary artifact through an agreed channel, and keep unrelated private material out of the handoff. For help defining the assignment itself, see [how to delegate tasks to AI agents](/blog/how-to-delegate-tasks-to-ai-agents).

## Failed checks, missing replies, and human decisions

A timeout does not mean the same thing as a failed test or a person who has yet to approve a merge:

<div style={{ minWidth: "620px", overflowWrap: "normal", wordBreak: "normal" }}>

| Situation | Next action |
|---|---|
| A diagnostic tool times out | Retry within a configured limit if repeating the action is safe; otherwise stop for the owner |
| The diagnosis lacks evidence | Ask for the missing information; do not advance to patching |
| The patch fails a relevant check | Return the failure evidence to the implementation owner |
| An agent does not respond | Record who is waiting, then notify the responsible person under the agreed timeout policy |
| A merge decision is pending | Preserve the reviewed version and pause until a decision arrives |

</div>
</div>

**Recovery depends on durable records and execution design.** A single agent can resume from saved progress; several agents can lose progress if nobody stores it.

Before retrying an action with external effects, check whether the first attempt already succeeded. Repeating a read is different from repeating a payment or sending a message twice. Set a retry limit and an escalation owner rather than instructing agents to keep trying indefinitely.

Creative work or an unusual exception may need a person to choose between proposals. Give that person the options and evidence, then record which decision lets work resume. The task can remain paused while they consider it. A design review, for example, can produce several drafts without granting any agent authority to publish one.

## Implementing AI agent orchestration

Choose by the decisions you need to control. **These layers can be combined**: a workflow can run agent code while people review its results in a room.

| Known steps and conditional transitions | Ordinary code or a workflow engine; inspect the [LangGraph workflow examples](https://docs.langchain.com/oss/python/langgraph/workflows-agents) for code-defined paths | State storage, validation, retry limits, and who handles failures |
| A manager chooses which specialist to call | An agent framework; follow the [Hugging Face manager-and-web-agent example](https://huggingface.co/learn/agents-course/en/unit2/smolagents/multi_agent_systems) | Delegate permissions, tool access, budget, result checks, and stop conditions |
| People review work from existing agents | A conversation and artifact-sharing space | Who accepts each handoff, where execution happens, and who resumes paused work |

</div>
</div>

For the bug report, a small implementation with transitions in code could record a task ID, diagnosis, patch revision, check results, and a pending decision. Permit the review step only when a patch revision exists; permit merge only after approval of that revision. A framework does not remove these requirements. If resuming after interruption matters, inspect its persistence configuration: [LangGraph's documentation](https://docs.langchain.com/oss/python/langgraph/persistence) explains checkpoints and checkpointers, rather than treating chat history as execution state.

For existing coding agents, also consider where people will inspect results and make decisions. [Claude Code and Codex on the same team](/blog/claude-code-and-codex-same-team) addresses that collaboration path.

For the signup report, a useful acceptance check is simple: can the next owner locate the evidence, identify the current patch, and tell whether to act or wait? If that answer is unclear, improve the handoff before adding another agent.

Once you have chosen how work should move, people and agents need a place to discuss it. If you already use Claude Code or Codex, [Alook](https://alook.ai) brings you, your coworkers, and your bots into the same room to review handoffs and exchange files. Each owner retains control of their bot's tools and runtime; room access does not automatically grant local file access or permission to execute tools. The conversation keeps the work visible, while your instructions and execution setup still govern sequencing, retries, and when to ask a person.
