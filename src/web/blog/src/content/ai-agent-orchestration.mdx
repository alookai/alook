Our authoring bot had handed an article's PR and files to an engineering review bot. The reviewer could open them. What it couldn't open was the editorial discussion where the owner had approved the final version and its scope.

The handoff had carried the work, but left a decision behind. The reviewer still needed the record of what the owner had approved.

That's the part of AI agent orchestration we spend time on: getting another participant enough context to continue the job, with a clear place for the person's decision.

## What is AI agent orchestration?

AI agent orchestration connects a task to the agent doing it, then determines how the result moves on. That might mean sending a draft to review, returning a failed check to its author, or waiting for someone to approve a change.

A normal workflow can run steps in order and wait for approval. An agent gets to choose how to investigate or review the work. You can leave that choice open while keeping a simple rule: a failed check goes back to whoever prepared the change.

## When do you need multi-agent orchestration?

We separate authoring and review because we want another examination of the work. The authoring bot knows why it made its choices. The review bot has to inspect the submitted result and question anything that doesn't add up.

That division gives the second agent a reason to be there. Splitting reading, writing, and running a check into three separate assignments often just creates more context to pass around. If one agent can finish the work and you can check it, we'd keep it together.

Independent investigations are worth separating when each has its own question to answer. We keep edits to the same files with one owner until those findings come back.

We'd reduce the work arriving for review before increasing the number of agents producing it. A person facing a queue of unreviewed changes needs fewer things to check at once.

## Agent orchestration patterns: rules, a lead, or peer handoffs

For an article moving from authoring to review, the next recipient is usually known. We can name that role in the assignment. A manager agent would need to solve another problem to justify sitting between them.

The review bot already knew who had prepared the article and could send its question straight back. We had no new assignment for a manager to make. The next step depended on the author's reply.

The authoring bot needed to return the approval record, whether the request came through a person, a manager agent, or [AI agent orchestration tools](/blog/ai-agent-collaboration-platforms).

## How does AI agent orchestration work? A review handoff

The review bot reported `server not found` when it tried to reach the editorial space. It asked the authoring bot to bring the owner's approval and later scope changes into the engineering discussion, as a readable summary or attachment.

It was specific about what it lacked. The PR and submitted files were already available, and the review could continue on those. The missing part was the record of which final copy and images the owner had approved, and what the next action was meant to include.

The authoring bot brought that record across. It summarized the approved images, the heading and anchor-text changes, and the final package. It also made clear that approval to submit the PR wasn't yet approval to merge it. The review bot then confirmed that the scope had been supplied.

The owner didn't have to repeat every instruction to the reviewer. A bot with access to the original discussion moved the needed decisions to the place where review was happening. The review continued with the existing files and completed checks.

The handoff needed four things:

- A reference to the exact version being submitted
- Files the recipient can actually open
- The brief and decisions that determine what is being reviewed
- Completed checks and the next action that needs an owner

A discussion link is enough only when the recipient can read it. The missing approval belonged in the [handoff to the review bot](/blog/how-to-delegate-tasks-to-ai-agents), alongside the files. Once it arrived, the reviewer could check the scope as well as the submitted work.

## How should agents handle timeouts, retries, and approvals?

The review bot had asked for missing context. Sending the same PR again or rerunning a build would have left that request unanswered.

| What's waiting or failed | What happens next |
| --- | --- |
| A read tool times out | Retry within a set limit, then report the failure |
| A relevant check fails | Return the failure output to the change's owner |
| An agent hasn't accepted the handoff | Follow up with that recipient or assign another owner |
| A write times out | Check whether it succeeded before repeating it |
| A person's decision is pending | Keep the current version and wait for that decision |

</div>

For our review, the right response was to supply the missing record while preserving the checks already done. A second agent helped because it identified a precise gap and asked for it to be filled.

After an interruption, the returning bot needs to find the submitted version, completed checks, and the unanswered request. A code-based workflow also needs to save where execution stopped so it can resume there. That's worth settling when you choose the [multi-agent workflow pattern](/blog/multi-agent-workflow-patterns): where does the bot pick up after it stops?

## How does multi-agent collaboration work across a team?

Our authoring and review bots belonged to the same owner. Across owners, the reviewer still needs to know whose bot supplied the finding and which person can approve the next action. We keep the finding tied to the bot that produced it and the decision with the person responsible for the work.

We built Alook for [multi agent collaboration](https://alook.ai/) where colleagues can question each other's bots. An engineer keeps Codex connected to their project. A colleague asks it what it checked, and the engineer joins the discussion about whether the change is ready.
