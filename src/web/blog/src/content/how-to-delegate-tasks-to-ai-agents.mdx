We ran into a chat-loading bug in Alook. Messages were already saved on the user's device, and the user had access to them, yet reopening a chat could leave them staring at a loading placeholder until a fresh network request finished.

One of us defined the expected behavior and the boundaries. Our agents took it from there: Jarvis coordinated, Samara built the fix, and Madox independently reviewed the code and tested it in the browser.

After the fix, saved messages showed up right away while the fresh request ran in the background, and the chat kept its existing rules for marking messages as read and enabling actions. Anyone scrolling through history stayed in place when the network response arrived. It worked across text channels, posts and threads, and private chats.

We knew the symptom and the reading behavior we wanted to keep. Samara's job was to find what held those messages back.

## Which coding tasks should you delegate to an AI agent?

We hand work to an agent when we know how to check the result and where the agent should bring open questions. A bug reproduction, a draft release note, and a list of outdated docs pages are all concrete enough to review quickly.

We also delegate investigations before we know the fix. With the chat bug, the symptom and the rules to preserve were clear, so tracking down what blocked rendering was straightforward engineering work. When we're still debating a product choice, we ask an agent to explore one option or build a small preview first.

Keep each batch small. A broad request can turn into a huge diff before anyone notices the agent went the wrong way. Start with one checkable piece, answer the next open question, and let the agent keep going.

## How to delegate coding tasks to AI agents in 5 steps

For a one-off task, your message is the trigger, and a small job only needs a few lines. If a key detail is missing, settle it in a quick exchange before the agent starts editing.

### 1. Choose one outcome you can check

“Make chat faster” leaves too much open. An agent might rewrite the cache, cut network requests, or add a spinner that hides the wait.

We picked a narrower goal: show messages already saved on the device while the refresh runs, without changing when messages count as read or when actions turn on. Samara tackled the delay inside those guardrails.

### 2. Gather the inputs and mark the unknowns

The bug hit text channels, posts and threads, and private chats. Each uses its own screen, so all three had to go into the brief. Sending a recording from just one screen would leave two-thirds of the bug untouched.

For an unfamiliar bug, share how to reproduce it and what you still don't know. For a recurring chore, write down the steps you already run by hand so the agent doesn't have to rediscover them.

Keep stable project rules in `AGENTS.md`, `CLAUDE.md`, or your existing repo docs. Put this task's failure, open questions, and target behavior directly in the brief.

### 3. Write the brief, including when to stop

**Vague instruction:**

> Handle this bug.

**Delegable instruction:**

```text
Trigger: the reported delay when reopening a chat
Goal: show messages already saved on the device while the refresh is pending

Inputs:
- reproduction notes and the affected conversation screens
- current message-display, read-state, and scrolling behavior

Scope:
- text channels, posts/threads, and private chats
- show only messages the person is allowed to see
- preserve when messages are marked read and when actions become available

Steps:
1. Reproduce the delay and identify what is holding back display.
2. Propose or make the scoped fix.
3. Check each affected screen, including scrolling during a late response.

Output:
- patch or findings, with the current branch/commit
- checks run, their results, and anything not checked
- remaining questions and the next requested action

Stop and ask if:
- who can see messages or when they count as read needs a product decision
- you can't reproduce the reported problem
- the fix requires changing behavior outside this scope
```

We built this brief from the fix requirements. The final patch touched 17 files across several components, so naming all three screens and the rules to preserve gave the agent clear boundaries before it knew which files to edit.

### 4. Review the work against the brief

A real review needs more than “take a look.” Hand the reviewer both the brief and the patch, and ask for concrete findings. If the read marker looks wrong, ask for exact steps to reproduce it.

### 5. Decide what to accept and what comes next

Check the returned work against the full brief. If only text channels were tested, posts and private chats still need verification. When review catches an issue and the agent updates the patch, check the new diff and fresh test output before accepting it.

## How do you know the AI agent actually finished?

Showing cached messages right away was safe because the user already had permission to read them. At the same time, read state, message actions, and scroll position during a late network response all had to keep working the same way.

We tested both the faster display and those surrounding rules. Automated tests covered rendering cached messages while read state or actions were still pending. Madox also ran browser checks across text channels, posts/threads, and private chats. Because the three screens are wired separately, each one needed its own browser pass.

The brief gives the reviewer sharp questions to check, such as whether showing cached messages marked them as read too early. Having the commit, test results, and any skipped or failing checks in one place makes that review much faster.

If you don't read code, start with something you can see directly. Ask the agent for a live preview or a short screen recording, including a simulated slow network. Here, you'd check that saved messages appear as soon as the chat reopens, the read marker follows the usual rules, and scrolling backward doesn't jump when the network response lands.

Code review and CI catch what a demo won't show. Check any edited tests closely, too: deleting or weakening an assertion can turn a broken change into a green build.

## How much authority should you give an AI agent?

Agree on the scope up front, then let the agent investigate, edit code, and run tests inside that boundary. If it has to ask permission before every routine command, you haven't really delegated the task.

You can let an agent write the patch and run tests while keeping merge and release rights with a specific person. Customer-facing messages work the same way: an agent can draft the reply, while a human decides whether to commit to it.

Settle two things before stepping away: what tools the agent can run, and what decisions it can make. For pure investigation, read-only repo access is enough. Fixing a bug requires permission to edit files and run tests, ideally in an isolated working copy.

Tool permissions and product authority are separate. Even when an agent can edit the codebase, product owners still decide rules like when a message counts as read.

When the agent hits an open product question, have it pause that part and report what it found alongside the decision needed. It can still finish independent work that falls within the agreed scope.

## How do you delegate a multi-day coding task to an AI agent?

On multi-day work, delegate the next slice you can verify, then shape the following step once those results come back.

Before ending a session, write a short handoff note next to the work. For example: “Patch is on this branch and commit. Channel checks passed; private-chat verification is still open. Existing read behavior is unchanged. Next, run the private-chat check against the attached reproduction, and ask before changing any unresolved behavior.”

Record rejected approaches and off-limits code paths whenever the next session might trip over them. When work resumes, the agent checks the actual files and test state against that note before making edits. Our guide to [keeping context across coding agent sessions](/blog/keep-context-across-coding-agent-sessions) covers where to store those notes.

For overnight runs, waking up to one clear question beats untangling hours of guesswork. Tell the agent who to ping when blocked and what to leave behind: the failure it hit, what it already tried, and the decision it needs. Anything blocked on that answer waits, and the machine or cloud runner has to stay online for the whole run.

## Before you hand over the task

- What should come back, and how will you tell it's done?
- Which files or links can the agent read, and what is still unknown?
- Which decisions or areas are off-limits?
- What proof should come back with the work, and who will review it?
- If the run stops early, where does the next person or session pick up?

## FAQ

### Should I review the AI agent's plan before it starts?

Review a plan when the direction itself needs your decision, such as a migration or a change to a public API. A small, well-understood fix can go straight to implementation within its agreed scope. You can refine the next step as you learn more.

### Should task instructions go in AGENTS.md or the prompt?

Put stable project guidance, such as build commands and recurring constraints, in the project's rules files. Keep this task's goal, current state, and open decisions with the task.

### Can I delegate a coding task if I can't read all the code?

Yes, if you can describe the behavior you want and have someone who reads code look at the result. Ask for a preview or recording you can inspect, along with the patch and checks for whoever reviews the code. Choose a smaller assignment when you can't yet tell how you'd accept the result.
