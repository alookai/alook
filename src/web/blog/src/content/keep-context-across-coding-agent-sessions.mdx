*Composite scenario for illustration, not a customer case study.*

You spend an hour with a coding agent sorting out an API boundary. You settle on GraphQL over REST, agree on error handling, and decide which endpoints belong to which service. Then the session ends.

Tomorrow you open a new session in the same repo without resume and without loading yesterday's notes. The agent can read the files. It does not have yesterday's thread in context. You re-explain the constraints. It suggests REST.

A new session usually starts with a cold context window. Continuity still lives in several places, each carrying a different slice of the work. This guide maps those carriers, how **agent memory** relates to context, and where the story still breaks. For why multi-agent work drifts in the first place, see [When AI Agents Don't Share Context or Memory](/blog/shared-context-between-agents).

## Context, agent memory, and what each one does

**Context** is the input information available to the model when it generates an answer. The **context window** is the capacity limit for that input and related output. Anthropic's [context engineering guide](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) treats the window as a capacity constraint, not a full archive of every prior message.

**AI agent memory** is how tools keep, organize, retrieve, and update information from earlier work so it can be selected again later. Claude Code's [memory docs](https://code.claude.com/docs/en/memory) and frameworks such as [LangChain's memory overview](https://docs.langchain.com/oss/python/concepts/memory) use related language: stored state can be retrieved; retrieved pieces can become context. Saving something does not mean it is already loaded, and loading it does not mean the model will use it correctly.

### AI agent memory system: persistent context

An **AI agent memory system** stores notes so they can outlive one chat window. Those stored notes provide **persistent context** when the next call retrieves and includes them. **AI agent persistent memory** can retain selected notes between sessions; the next run still has to retrieve and check them.

Keep four carriers separate:

- **Rules files** (`CLAUDE.md`, `AGENTS.md`, Cursor rules)
  - What it is: stable instructions loaded into new sessions
  - What it is not: a replay of Tuesday's chat
- **Session history / resume**
  - What it is: a record or checkpoint of one product's thread
  - What it is not: guaranteed full transcript replay across tools
- **Product memory** (e.g. Claude auto memory)
  - What it is: notes the tool stores for later sessions
  - What it is not: cross-machine or cross-vendor sync by default
- **Handoff markdown**
  - What it is: a portable WIP story you maintain
  - What it is not: automatic notification or always-fresh truth

Short-term memory can still be persisted (for example, thread-scoped checkpoints in LangGraph). Do not treat “short-term” as “never saved.”

## Coding agent sessions start with a cold context window

Claude Code and Cursor both treat a new session as a cold conversational start.

[Claude Code's memory docs](https://code.claude.com/docs/en/memory) say each Claude Code session begins with a fresh context window. What loads next is not the full chat. It is instruction files you maintain, plus auto memory Claude writes for later sessions.

[Cursor's rules docs](https://cursor.com/docs/rules.md) draw the same line: large language models do not retain memory between completions. Project rules and `AGENTS.md` inject instructions into the prompt. They do not replay yesterday's thread.

"Remembering the project" is not the same as "remembering Tuesday's thread." The agent can see the codebase. It cannot see the reasoning that shaped it unless that reasoning lives somewhere durable and then gets selected into context.

What survives a session boundary depends on which carriers you use.

## Put durable agent rules in CLAUDE.md and AGENTS.md

Start with `CLAUDE.md`, `AGENTS.md`, and Cursor project rules under `.cursor/rules`. Cursor also documents `AGENTS.md` as a plain-markdown alternative to `.cursor/rules`.

**What continues:** coding standards, architecture constraints, build and test commands, naming conventions, "always do X" rules. These load at session start and spare the agent from rediscovering project basics.

**Where it breaks:** stable files do not carry this week's WIP, the decision you made Tuesday, or which PR is blocked on review. If the fact changes weekly, it does not belong in a file meant to stay useful for months.

**Practice:** keep instruction files lean. Claude's [best practices](https://code.claude.com/docs/en/best-practices) say `CLAUDE.md` should hold persistent context the agent cannot infer from code alone, and advise keeping the file short so important rules are not lost. The [memory docs](https://code.claude.com/docs/en/memory) target under about 200 lines per `CLAUDE.md`. Prefer pointers to canonical files over pasting a whole style guide into every session.

## Carry decisions in commits and pull requests

Commits, PR descriptions, branch names, review threads.

**What continues:** what landed in the tree. Reasoning written into PR descriptions or commit bodies is readable to the next agent. Branch names like `feat/graphql-gateway` signal intent before anyone opens a file.

**Where it breaks:** Git records what you shipped. It does not record what you considered and rejected unless someone wrote that down. GraphQL over REST lives in a PR comment only if it was typed there. Otherwise the next session sees the implementation without the rationale.

**Practice:** when a decision will matter to a later session, put the *why* in the commit body or PR description. Treat Git as code truth. For decision truth, you usually need another carrier.

## Resume one runtime without expecting automatic cross-tool memory

### How to persist memory across agent sessions

Inside one product, use that product's memory store and resume. Across tools, write a repo handoff file the next runtime can read. Neither path syncs private stores automatically.

Claude Code auto memory and `claude --continue` / `claude --resume`; multi-agent work inside Codex's own product surfaces. This is where **persistent agent memory** usually shows up in coding tools: a store that can outlive one chat window inside that product.

**What continues (same runtime, same machine):** Claude Code can save notes (build commands, debugging patterns, preferences) under `~/.claude/projects/<project>/memory/`. At session start it loads the first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first; other topic files load on demand ([how it works](https://code.claude.com/docs/en/memory#how-it-works)). Auto memory is local to that machine and shared across worktrees for the same repo; it does not automatically sync across machines or cloud environments.

To reopen work in that same product, [best practices](https://code.claude.com/docs/en/best-practices) document `claude --continue` for the most recent session and `claude --resume` to pick from a list. Codex ships a [local CLI](https://github.com/openai/codex) and a separate app experience; agent work there stays inside OpenAI's surfaces, not inside Claude Code.

**Example: save → retrieve → select → verify (Claude auto memory):**

1. **Save:** end of day, ask Claude Code to write “use GraphQL gateway; do not reopen REST debate” into project auto memory. Confirm the note appears under `~/.claude/projects/<project>/memory/` (in `MEMORY.md` or a topic file such as `api-boundary.md`).
2. **Retrieve next session:** on the same machine, open the same repo and start Claude Code so startup can load `MEMORY.md` (first 200 lines or 25KB, whichever comes first). If the note lives in a topic file, open or `@`-mention that file so it is actually read, not only stored.
3. **Select into context:** ask the agent to quote the GraphQL decision from that memory file before proposing API edits.
4. **Verify freshness:** open the latest PR for the gateway change and check the memory note still matches the PR description and current branch; if the decision changed, update or delete the memory entry before more edits.

Saved ≠ fully loaded. Loaded ≠ still true.

**Where it breaks:** Claude's auto memory does not reach Codex by itself, and Codex sessions do not load into Claude Code. Resume restores one product's history, not another tool's private store. Shared repo files or an integration can still bridge work; there is no automatic private-store sync across vendors or machines.

**Practice:** manage context aggressively inside one runtime. Claude's best practices recommend `/clear` between unrelated tasks and using subagents for investigation so exploration does not clutter the main thread. Do not mistake per-runtime memory for cross-tool continuity.

## Keep nested agents inside one product ecosystem

Claude Code [subagents](https://code.claude.com/docs/en/sub-agents) and [Agent Teams](https://code.claude.com/docs/en/agent-teams); multi-agent workflows inside Codex's own app/CLI ecosystem.

**What continues:** work that stays inside one ecosystem. Subagents run scoped tasks and return results to the parent. Product-native teams and in-product multi-agent flows can organize multi-step work without leaving that vendor's walls.

**Where it breaks:** when work must move Claude Code → Codex (or Cursor, or another machine), native orchestration does not bridge private ownership and task status by itself. For the dual-runtime case, see [bringing Claude Code and Codex into the same team](/blog/claude-code-and-codex-same-team). ## Write a handoff file before the next coding session

**How to add memory to AI agent sessions:** put the working story in a file the next session can open.

A `HANDOFF.md`, `STATUS.md`, or short notes file at a fixed path in the repo. Treat it as a portable memory artifact you control, not as the same thing as product auto memory.

![Handoff.md template: goal, done, changed paths, verified, next step, do not touch](/blog/keep-context-across-coding-agent-sessions/handoff-template.webp)

[Open the full-size handoff template](/blog/keep-context-across-coding-agent-sessions/handoff-template.webp).

**What continues:** current goal, what was done, what changed, what to verify, what not to touch, and who owns the next step, if the outgoing session writes it before closing and the next session reads it before editing.

Use the same save → read → verify habit as the Claude memory example above, but write the artifact to a fixed repo path such as `docs/HANDOFF.md`. That is the main difference: product auto memory stays inside one tool and machine; a handoff file can be opened by any runtime that can read the repo, including after you switch tools.

**Where it breaks:** a handoff nobody updates is worse than none. It needs a habit: write at task end, read at task start. It does not notify you. Do not ask one agent to summarize another agent's transcript as the primary bridge. Write the conclusions directly.

**Practice:** fix the path (`docs/HANDOFF.md` or similar). Use a short template: done / changed / verified / not done / next step / do not touch. Open-source tools such as [context-bridge](https://github.com/yagyaanshK/context-bridge) treat continuity as a local markdown handoff (and warn against relying on one AI to summarize another as the core bridge).

## Where each layer stops

![Context carriers: what each layer continues and where it breaks](/blog/keep-context-across-coding-agent-sessions/carrier-map.webp)

[Open the full-size carrier map](/blog/keep-context-across-coding-agent-sessions/carrier-map.webp).

- **Instruction files:** retain stable rules and architecture. They do not track live work or weekly decisions.
- **Git / PR:** retain code changes and written review. Unwritten decisions are missing.
- **Session resume / auto memory:** retain one tool's history or notes. Other runtimes and machines do not load private stores automatically.
- **Nested agents / in-product multi-agent:** coordinate inside one ecosystem. Cross-runtime ownership still needs a bridge.
- **Handoff markdown:** carries a portable work summary. It fails when the note is stale or nobody maintains it.
- **Coordination layer:** connects roles, threads, and task status across agents. The next section explains its scope.


If work stays inside one runtime and you maintain project files, these layers cover most cases. The gap opens when you run multiple agents, switch runtimes, or need decisions to move between sessions without you carrying them by hand.

## Connect sessions when files and git are not enough

The layers above still leave you as the sync point: read one session's output, paste into the next, or maintain a handoff no agent refreshes on its own.

When that bridging is daily, the missing piece is not only “more memory files.” It is a channel between sessions: persistent identity so work can address a specific agent, explicit task ownership, and threads that survive restarts on both sides.

We built [Alook](https://alook.ai) as that coordination layer for local coding agents. Agents keep their own runtimes and in-tool memory. Alook adds roles, persistent message threads, and handoffs that outlast a single chat window. It does not merge every bot's private runtime memory. See [supported agents](/blog/ai-agent-team#supported-agents) for the current runtime list, and [how to build an AI agent team](/blog/ai-agent-team) for roles and handoffs.

Context can persist in files, in Git, in runtime memory, in handoff notes. Each carries something. None carries everything. The more agents and sessions you run, the more useful it becomes to connect them rather than reconciling them yourself.

## FAQ

**What is agent memory for coding agents?**  
**Agent memory** is how a coding agent keeps, organizes, and later retrieves information from earlier work. Retrieved pieces can become context for a new call; saving something does not mean it is already loaded.

**Do CLAUDE.md or AGENTS.md restore my last chat?**  
No. They load instructions into a new session. They are not a transcript replay.

**Is session resume enough when I switch from Claude Code to Cursor?**  
Usually not by itself. Resume and product auto memory stay with the tool that stored them. Shared files or an integration can bridge work, but private stores do not sync automatically.

**What belongs in a handoff file?**  
Goal, done, changed paths, verified checks, not-done or blocked items, next step, and do-not-touch notes. Rewrite the file at each handoff, then re-check it for stale facts before the next edit.

**How to give AI agent memory for past interactions**  
Save a compact record (product memory note or repo handoff), retrieve it in the next session, select only what the current task needs into context, then verify it against the current branch. That is not a full chat replay.

**How do I add memory to my AI agent?**  
**How do I give an AI agent persistent memory?**  
Pick the tool's native memory when you stay in one runtime, or a repo handoff when you may switch tools. Write the note, confirm where it lives, load or `@`-mention it next time, and update or delete it when the decision changes. Persistent storage still needs an explicit read.

**When do you need more than files and git?**  
When work crosses runtimes or spans days and you need owned next steps plus a thread you can reopen without reconstructing the chat.
