You spend an hour with a coding agent sorting out an API boundary. Together you pick GraphQL over REST, agree on error handling, and split endpoints across services. Then you close the terminal.

The next morning, you open a fresh session in the same repo without resuming the old chat or loading any notes. The agent can read your code, sure, yet yesterday's conversation is gone. You explain the requirements again, and its first suggestion is REST.

A new session usually starts with a cold context window rather than replaying prior chat. To carry work forward, you rely on a handful of files and built-in features, and each one keeps a different piece of the picture. Here is how **agent memory** relates to context, what survives between sessions, and where things still fall through the cracks. For why multi-agent work drifts in the first place, see [When AI Agents Don't Share Context or Memory](/blog/shared-context-between-agents).

## Context, agent memory, and what each one does

**Context** is whatever text is actually inside the prompt when the model writes a reply. The **context window** is how much fits at once. As Anthropic's [context engineering guide](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) puts it, treat that window as a working budget rather than an archive of every past message.

**AI agent memory** is how a tool saves, organizes, and pulls back notes from earlier sessions so you can reuse them later. Both Claude Code's [memory docs](https://code.claude.com/docs/en/memory) and [LangChain's memory overview](https://docs.langchain.com/oss/python/concepts/memory) draw the same distinction: saved notes sit in storage until something retrieves them into context. Just because a note is saved on disk doesn't mean the next session loaded it, and loading it doesn't guarantee the model will follow it.

### AI agent memory system: persistent context

An **AI agent memory system** keeps notes alive past a single chat window. Those notes provide **persistent context** only when the next run retrieves and includes them. Even with **AI agent persistent memory**, the new session still has to read those notes and verify they match the current code.

It helps to separate four ways state carries over:

- **Rules files** (`CLAUDE.md`, `AGENTS.md`, Cursor rules)
  - What they are: standing project instructions loaded at session start
  - What they aren't: a transcript of Tuesday's chat
- **Session history / resume**
  - What it is: a saved thread or checkpoint inside one tool
  - What it isn't: portable history that carries over to other tools
- **Product memory** (such as Claude auto memory)
  - What it is: notes the tool writes down for future sessions on that machine
  - What it isn't: something that syncs across machines or vendors automatically
- **Handoff markdown**
  - What it is: a short work-in-progress note you keep in the repo
  - What it isn't: a live alert or a guarantee that the notes are still current

Note that short-term memory can still be saved to disk (for example, thread-scoped checkpoints in LangGraph), so don't read "short-term" as "never saved."

## Coding agent sessions start with a cold context window

Both Claude Code and Cursor start a new session cold, without automatically carrying over your previous conversation.

According to [Claude Code's memory docs](https://code.claude.com/docs/en/memory), each session opens with a fresh context window. Instead of replaying your old chat, startup loads the instruction files you maintain along with any auto-memory notes Claude saved earlier.

[Cursor's rules docs](https://cursor.com/docs/rules.md) draw the same boundary: language models don't retain memory between completions. Project rules and `AGENTS.md` inject standing instructions into the prompt, leaving yesterday's back-and-forth behind.

Knowing how a codebase is laid out is very different from remembering what you decided on Tuesday. Any agent can inspect your files, while the reasoning behind them disappears unless you record it somewhere durable and pull it into the next session's context.

What survives between sessions comes down to which carriers you use.

## Put durable agent rules in CLAUDE.md and AGENTS.md

Start with `CLAUDE.md`, `AGENTS.md`, and Cursor project rules under `.cursor/rules` (Cursor also supports plain-markdown `AGENTS.md` files).

**What carries over:** coding standards, architecture constraints, build and test commands, naming conventions, and "always do X" rules. Because these load at startup, the agent doesn't have to rediscover basic project conventions every time.

**Where it falls short:** static rule files don't hold this week's work-in-progress, a design call from Tuesday, or which PR is blocked on review. If a detail changes every few days, keep it out of a file meant to hold long-term rules.

**In practice:** keep instruction files short. Claude's [best practices](https://code.claude.com/docs/en/best-practices) recommend reserving `CLAUDE.md` for durable context the agent can't infer from code alone, so critical rules don't get buried. The [memory docs](https://code.claude.com/docs/en/memory) aim for under roughly 200 lines per `CLAUDE.md`. Link to canonical docs in the repo rather than pasting an entire style guide into every session.

## Carry decisions in commits and pull requests

Git already carries plenty of context through commits, PR descriptions, branch names, and review comments.

**What carries over:** everything that landed in the tree, plus whatever reasoning people wrote down. Branch names like `feat/graphql-gateway` signal intent before anyone opens a file, and commit bodies or PR descriptions stay readable to the next agent.

**Where it falls short:** Git shows what you shipped, while alternatives you ruled out vanish unless someone wrote them down. Picking GraphQL over REST only survives in Git if someone explained it in a commit or PR comment. Otherwise, the next session sees the code without the rationale.

**In practice:** whenever a design choice will matter later, put the *why* in the commit body or PR description. Git handles code truth; ongoing design context usually needs another home.

## Resume one runtime without expecting automatic cross-tool memory

### How to persist memory across agent sessions

When you stay inside one tool, use its built-in memory store and session resume. When you switch tools, write a handoff file in the repo that the next runtime can open. Private tool stores never sync across vendors on their own.

In everyday coding tools, **persistent agent memory** usually means tool-specific storage that outlives one chat window: Claude Code offers auto memory plus `claude --continue` and `claude --resume`, while Codex keeps multi-agent threads inside its own CLI and app.

**What carries over (same runtime, same machine):** Claude Code can save project notes (build commands, debugging patterns, preferences) under `~/.claude/projects/<project>/memory/`. When auto memory is enabled, startup loads the first 200 lines or 25KB of `MEMORY.md`, whichever limit hits first, and reads extra topic files on demand ([how it works](https://code.claude.com/docs/en/memory#how-it-works)). Auto memory stays local to that machine and shares across worktrees for the same repo, without syncing across machines or cloud environments.

To reopen earlier work in Claude Code, the [best practices](https://code.claude.com/docs/en/best-practices) cover `claude --continue` for the latest session and `claude --resume` to pick an older one. Codex ships its own [local CLI](https://github.com/openai/codex) and app, and session history there stays inside OpenAI's tools rather than loading into Claude Code.

**Example: save → retrieve → select → verify (Claude auto memory):**

1. **Save:** at the end of the day, ask Claude Code to record "use GraphQL gateway; do not reopen REST debate" in project auto memory. Check that the note appears under `~/.claude/projects/<project>/memory/` (in `MEMORY.md` or a topic file like `api-boundary.md`).
2. **Retrieve next session:** on the same machine, open the repo and launch Claude Code so startup can load `MEMORY.md` (first 200 lines or 25KB, whichever comes first). If the note lives in a separate topic file, open or `@`-mention that file so Claude actually reads it instead of leaving it on disk.
3. **Select into context:** ask the agent to repeat the GraphQL decision from that memory file before proposing API edits.
4. **Verify freshness:** check the latest gateway PR and current branch to confirm the memory note still matches reality. If plans changed, update or delete the note before editing code.

Saving a note doesn't mean the next session loaded all of it, and loading it doesn't mean it's still accurate.

**Where it falls short:** Claude's auto memory doesn't carry over to Codex, and Codex sessions don't open in Claude Code. Session resume only brings back one product's history. Repo files or an external integration can bridge tools, since private stores stay separate across vendors and machines.

**In practice:** keep context lean even inside one runtime. Claude's best practices suggest running `/clear` between unrelated tasks and using subagents for codebase exploration so dead ends don't clutter your main chat. Just don't count on built-in tool memory when you jump between runtimes.

## Keep nested agents inside one product ecosystem

Tools like Claude Code [subagents](https://code.claude.com/docs/en/sub-agents), [Agent Teams](https://code.claude.com/docs/en/agent-teams), and Codex's built-in multi-agent workflows let a session spin up helper agents for focused work.

**What carries over:** multi-step work inside that single tool. Subagents run scoped tasks and return summaries to the parent session, keeping delegation inside one vendor's runtime.

**Where it falls short:** as soon as work moves from Claude Code to Codex, Cursor, or another machine, built-in subagents can't carry task ownership or status across the gap. ## Write a handoff file before the next coding session

**How to add memory to AI agent sessions:** write the current working state into a repo file that the next session can read.

Use a plain markdown file like `HANDOFF.md` or `STATUS.md` at a fixed path in the repo. Unlike built-in auto memory, this is a portable file you control directly.

![Handoff.md template: goal, done, changed paths, verified, next step, do not touch](/blog/keep-context-across-coding-agent-sessions/handoff-template.webp)

[Open the full-size handoff template](/blog/keep-context-across-coding-agent-sessions/handoff-template.webp).

**What carries over:** the current goal, completed steps, modified paths, verified checks, off-limits files, and who owns the next step, provided the outgoing session writes it before closing and the incoming session reads it before editing.

Follow the same save, read, and verify habit from the Claude memory example above, writing to a standard repo path like `docs/HANDOFF.md`. Because the file lives in the repo instead of a private tool folder, any runtime can read it even after you switch editors or CLIs.

**Where it falls short:** an outdated handoff file causes more confusion than having none at all. It relies on discipline: write at task end, read at task start. A markdown file won't ping anyone on its own, either. Avoid asking one agent to summarize another agent's raw chat transcript as your main handoff; write down the settled conclusions directly.

**In practice:** standardize on one path like `docs/HANDOFF.md` and a short template: done, changed, verified, not done, next step, and do not touch. Open-source utilities like [context-bridge](https://github.com/yagyaanshK/context-bridge) take the same local-markdown approach and warn against chaining AI transcript summaries.

## Where each layer stops

![Context carriers: what each layer continues and where it breaks](/blog/keep-context-across-coding-agent-sessions/carrier-map.webp)

[Open the full-size carrier map](/blog/keep-context-across-coding-agent-sessions/carrier-map.webp).

- **Instruction files:** hold stable rules and architecture, not active work or weekly decisions.
- **Git / PR:** record code diffs and written review comments, while unwritten tradeoffs disappear.
- **Session resume / auto memory:** keep one tool's history or notes on one machine, without syncing across runtimes.
- **Nested agents / in-product multi-agent:** coordinate steps inside a single vendor's tool, stopping at cross-runtime boundaries.
- **Handoff markdown:** gives any tool a portable status summary, until someone forgets to update it.
- **Coordination layer:** connects roles, threads, and task status across separate agents, covered next.

If you stay in one runtime and keep your repo docs tidy, the first five layers handle most day-to-day coding. You feel the gap once you run multiple agents, mix runtimes, or spend time copying decisions from one chat window into another.

## FAQ

**What is agent memory for coding agents?**  
**Agent memory** is how a coding agent keeps, organizes, and later retrieves information from earlier work. Retrieved pieces can become context for a new call; saving something does not mean it is already loaded.

**Do CLAUDE.md or AGENTS.md restore my last chat?**  
No. They load instructions into a new session. They are not a transcript replay.

**Is session resume enough when I switch from Claude Code to Cursor?**  
Usually not by itself. Resume and product auto memory stay with the tool that stored them. Shared files or an integration can bridge work, but private stores do not sync automatically.

For a practical setup, see how to [use Claude Code and Cursor together](/blog/cursor-vs-claude-code#using-claude-code-and-cursor-together) while keeping their sessions separate.

**What belongs in a handoff file?**  
Goal, done, changed paths, verified checks, not-done or blocked items, next step, and do-not-touch notes. Rewrite the file at each handoff, then re-check it for stale facts before the next edit.

**How to give AI agent memory for past interactions**  
Save a compact record (product memory note or repo handoff), retrieve it in the next session, select only what the current task needs into context, then verify it against the current branch. That is not a full chat replay.

**How do I add memory to my AI agent?**  
**How do I give an AI agent persistent memory?**  
Pick the tool's native memory when you stay in one runtime, or a repo handoff when you may switch tools. Write the note, confirm where it lives, load or `@`-mention it next time, and update or delete it when the decision changes. Persistent storage still needs an explicit read.

**When do you need more than files and git?**  
When work crosses runtimes or spans days and you need owned next steps plus a thread you can reopen without reconstructing the chat.
