Matt Pocock was planning future features when a side task came up. He wanted to move iteration and completion signals to a different API. He told his agent why he wanted to hand it off and what the document needed to cover. His `/handoff` skill wrote that document, and he passed it to another agent to create an issue. He could keep planning without losing the task or the discussion behind it.

His [handoff demonstration](https://www.youtube.com/watch?v=dtAJ2dOd3ko) shows why that note matters. A fresh agent can read the code. The code alone may not explain why it looks that way. The detail we would hate to lose is the evidence behind a rejected approach: the error, check, or constraint that stopped it the first time.

## What does a new coding agent session already know?

A fresh agent can inspect the current code and Git history and load project instructions. None of those reveal an abandoned approach unless you wrote it down. Matt's prototype shows the difference. He sent a difficult part of a planning session to another agent. By the time the prototype session reached 169,000 tokens, he wanted to bring its discoveries back to the planner. He asked for a handoff covering what wasn't obvious from the prototype itself. The code showed what he'd built. The note carried what he'd learned.

A project file tells an agent which test command the team uses. A pull request shows what changed and sometimes why. Neither automatically captures the discussion that led someone to reject a different approach.

Claude Code can read a repository's `AGENTS.md` as project instructions in place of `CLAUDE.md`. By default, it chooses `AGENTS.md` when there are no project `CLAUDE.md` or `CLAUDE.local.md` instructions in the working directory or above it. Auto memory is on by default in local sessions. Claude loads a short index at startup when auto memory is enabled, then reads further notes as needed. The [Claude Code memory guide](/blog/claude-code-memory) covers the settings. [Codex memory](/blog/codex-memory) has its own settings and storage.

Resuming the same session is a good start. After compaction, the tool might continue from a summary rather than every earlier message. If the error or number you need is missing, return to the original record before acting.

You might recognize the moment: a fresh session confidently suggests the fix you ruled out an hour ago. The summary kept the plan, but the error that changed it is missing. We prefer to give the agent that error instead of asking it to reconstruct the whole investigation. It has something specific to check before it repeats the work.

## What should a handoff carry?

A goal alone leaves the agent to guess how you got there. Give it the decisions and their reasons, especially the paths that led nowhere. Add the checks already run and what remains to do. The branch or pull request can show the diff.

One developer described a handoff from Cursor to Claude Code that buried an important constraint. Cursor had drafted part of a script. The handoff told Claude not to touch authentication, but Claude overlooked that note and rewrote the auth path. The developer moved the constraint to the top afterward.

Discarded approaches leave no code behind. If you investigated an option and found it couldn't work, say what you tried and why you set it aside. Otherwise another session can repeat the same investigation.

The reason can be short. Keep the evidence that settled it, even an untidy error message. A failed command or an error message tells the agent what to verify. “We tried another approach” does not. A link to a review gives the agent a way to inspect the decision without copying the whole discussion. “Tests passed” doesn't say whether someone ran one focused check or the whole suite. A failed check needs investigation. An unrun check needs a decision about whether to run it.

Here is a handoff you can copy:

```markdown
Handoff
===

## Goal
[What needs to be completed, and why]

## Do not touch
[Files, behavior, or boundaries to preserve]

## Decisions and evidence
[Decision, reason, and link to the relevant review or result]

## Approaches ruled out
[What you tried, the error or evidence, and why you stopped]

## Checks
[Command or test, result, and what was not run]

## Decision needed
[What needs a decision, who needs to make it, and the evidence]

## Current state and next action
[Branch or change, unfinished work, and the next concrete step]
```

Replace the placeholders and remove anything that doesn't apply.

Before continuing, compare the handoff with the branch and the latest test results. Someone might have merged a change or rerun a test since the note was written. If they disagree, find out which version is current before editing.

## How do you carry context from Claude Code to Codex?

Matt's skill writes the handoff to the operating system's temporary directory. The file can travel between tools without either one understanding the other's session history. To move from Claude Code to Codex, choose a location Codex can read, then give it the path and the task it should take over. Include the branch or change the note describes. Ask Codex to compare the note with the code and follow the evidence behind any constraint.

Claude Code supports text messages between a user's own sessions, but those messages don't bring the sender's files or conversation. [Bringing Claude Code and Codex together](/blog/claude-code-and-codex-same-team) covers working copies and review.

One developer worried about Claude Code and Codex sharing a `HANDOFF.md`. Each agent might rewrite the history around its own recent work. The developer suggested an append-only record so earlier decisions remain visible.

We would rather read a messy history than a tidy summary that dropped why the plan changed. An append-only decisions section keeps earlier choices visible. Someone can check a new entry against the work before treating it as the current decision.

If both tools edit in parallel working copies, [multiple agents editing the same repository](/blog/multiple-ai-agents-edit-same-repository) explains what can go wrong.

## When the next session belongs to a teammate

A note can be enough when you move between your own tools. You already know why the task matters and where the work is. A colleague starts with less. You might know why a result matters, but they only see what you send. Fill in the template’s “Decision needed” section with the question, who can answer it, and the evidence they need. Then the colleague and their agent can discuss the same question without asking you to relay it.

In Alook, people and their agents can discuss a task together in a thread. The [multi agent collaboration workspace](/blog/introducing-alook) keeps the question alongside the conversation and shared files.

## Should a handoff file be committed?

We prefer to commit a handoff when colleagues need it alongside the code. It makes the note easier to find with the change. Keep a personal or sensitive note outside the repository, where it won't travel with every clone. Either way, tell the receiving session where to find it.
