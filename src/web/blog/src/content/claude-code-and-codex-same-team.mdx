**Yes, Claude Code and OpenAI Codex CLI can work together on the same project.** One agent makes a change and the other reviews it, and a person approves the final merge or release. If both agents edit at once, each gets a separate working copy, and the handoff spells out what the reviewing agent should do next.

A [manual handoff](#what-to-include-in-a-claude-code-and-codex-handoff) is enough for an occasional task, and the [official plugin](#use-the-official-codex-plugin-for-claude-code) brings a Codex review into Claude Code. Teammates who exchange work regularly can keep the discussion in one place with a [shared channel](#bring-claude-code-codex-and-humans-together).

Some older tutorials have Claude Code start `codex mcp-server`, but OpenAI has removed that command, so any integration built on it needs a replacement. If you run one of those setups, see the [Codex MCP alternatives](#what-happened-to-the-old-codex-mcp-setup).

You don't have to write code to use this workflow, though someone still needs to look after tests and merges. Parallel edits are covered in the [Git worktrees section](#git-worktrees-and-separate-checkouts-for-parallel-edits).

## How a Claude Code and Codex workflow runs

Start with one scoped task and a clear definition of done. One agent implements the change, and the other waits or takes a task that doesn't overlap. Whichever agent did the work sends the other a specific commit or working state, plus the decisions and checks behind it. Either agent can implement or review, and the right split depends on the task.

## What to include in a Claude Code and Codex handoff

- **Goal:** what this task should achieve
- **Working state:** checkout, branch, commit when available, and any uncommitted changes that matter
- **Files changed:** the intended scope of the edit
- **Decisions:** what was chosen, rejected, or left undecided
- **Checks:** tests, linters, builds, or manual checks already run
- **Open questions:** risks or blockers that still need judgment
- **Next action:** review, revise, test, or escalate to a person

### Have Claude Code and Codex review each other's code

Claude Code makes the change and Codex reviews the diff, or the two agents swap roles. Findings go back to the agent that made the change, which fixes the issue and shares a new commit. The reviewing agent checks that revision, and whoever merges looks at the version that will ship.

![A five-step review flow: Claude Code implements, Codex reviews, Claude Code fixes the findings, Codex rechecks, and a person approves the reviewed version](/blog/claude-code-and-codex-same-team/review-loop-20261015.png)

*Either tool can build or review; a person approves the reviewed version.*

### Resume a session or pass a handoff

Closing a terminal doesn't always lose your context, since [Claude Code can resume saved sessions](https://code.claude.com/docs/en/common-workflows#resume-previous-conversations). A fresh session starts without that history, so save the working files or make a commit, then hand the new agent the decisions and the next action.

Shared project instructions hold standing rules, not the latest review comments. If a teammate needs the chat log itself, use our [Claude Code session-sharing guide](/blog/share-claude-code-session), and send the working files separately.

## Four ways to use Claude Code and Codex together

Pick a setup based on who takes part and how often work changes hands. The four below describe how people and agents coordinate, while the [MCP section](#what-happened-to-the-old-codex-mcp-setup) compares ways for Claude Code to call Codex. If your work spans both tools, you can use whichever of those ways fits.

**One small or experimental task**

- **Start with:** Manual handoff
- **What it handles:** Full human control with almost no setup
- **Main limitation:** You carry every update between sessions

**Code moving between implementer and reviewer**

- **Start with:** Git branches, commits, and pull requests
- **What it handles:** Diffs, code history, and review
- **Main limitation:** Git does not assign the next owner or preserve every decision

**The whole job stays inside one product**

- **Start with:** Claude Code subagents or Codex threads
- **What it handles:** Parallel work inside one runtime
- **Main limitation:** It does not connect independent Claude Code and Codex sessions

**The same workflow repeats across both tools**

- **Start with:** A shared workspace such as Alook
- **What it handles:** Teammates work directly with each other's bots, with persistent identities and saved context
- **Main limitation:** Bots need their connected computers online; setup may be unnecessary for one-off work

[Claude Code subagents](https://docs.anthropic.com/en/docs/claude-code/sub-agents) each run in their own context window and report back to a main Claude Code session. The [Codex app](https://openai.com/index/introducing-the-codex-app/) runs several agents in parallel, in separate threads with isolated repo copies. Neither one shares its private session history with the other product.

### Use the official Codex plugin for Claude Code

To connect and call Codex from Claude Code, install the [official Codex plugin](https://github.com/openai/codex-plugin-cc) by running these commands in Claude Code:

```text
/plugin marketplace add openai/codex-plugin-cc
/plugin install codex@openai-codex
/reload-plugins
/codex:setup
```

The plugin needs Node.js 18.18 or later, plus either a ChatGPT account (Free included) or an OpenAI API key. The setup command checks that your local Codex install is ready and signed in. After setup, you have four commands:

- `/codex:review` requests a read-only review.
- `/codex:adversarial-review` challenges a plan or change with a review you can steer.
- `/codex:rescue` delegates a task such as investigating or fixing a bug.
- `/codex:transfer` imports the current Claude Code session into a persistent Codex thread and returns a command to resume it (requires a Codex version with session-import support).

For a first review, ask Codex to check the current branch against its base (replace `main` below with your project's base):

```text
/codex:review --base main --background
```

While a review runs, `/codex:status` shows its progress, and `/codex:result` returns the findings. The review is read-only, so Claude Code can talk through those findings before it edits anything.

The plugin wraps the Codex app server and relies on your local Codex installation, sign-in, configuration, and repository checkout. **Pause other edits whenever you delegate changes in that same checkout.** It doesn't spin up an isolated working copy, and it doesn't continuously sync both tools' private conversations.

### Git worktrees and separate checkouts for parallel edits

If you don't manage code, you can skip this section.

**Git branches separate commit history, not files on disk.** If two agents edit the same working directory, they can overwrite each other's files. Give each parallel task a branch and a separate checkout, whether that's a Git worktree, a clone, or a container.

```text
implementation checkout: branch feature/payment-copy
review checkout: detached at the handed-off commit, or reviewing its PR
```

A read-only review doesn't need its own branch. If the reviewing agent will change files, cut a new branch from the handed-off commit, and merge only after dependencies, conflicts, and tests check out. When both agents need to touch the same file, let one finish editing before the other reviews or suggests changes.

## What changed with the old Codex MCP server?

Some Claude Code tutorials register `codex mcp-server` so Claude can call Codex through the Model Context Protocol (MCP). OpenAI has [removed that command and the standalone `codex-mcp-server` binary](https://learn.chatgpt.com/docs/mcp-server), so if a configuration launches either one, it needs a new integration before you upgrade.

The removed command exposed Codex as a server. Codex can still act as a client and connect to external MCP servers, and `codex mcp` manages those connections.

On November 26, 2026, `codex --help` on our Codex CLI 0.164.0 listed `mcp` for managing external servers but did not list `mcp-server`. OpenAI's [0.154.0 release notes](https://github.com/openai/codex/releases/tag/rust-v0.154.0) also record the removal of the old entry point. If an integration fails after an upgrade, look for `codex mcp-server` in its configuration.

### Choose a replacement for the work you need

For a single review inside Claude Code, we'd start with the official plugin above. Its slash commands ask Codex for a review, there's no MCP bridge to set up, and OpenAI maintains the plugin itself.

For scripts or custom shell workflows, `codex exec` runs Codex non-interactively and `codex review` runs a review, and your script handles the output. On 0.164.0, `codex exec --help` lists `--model` and `--sandbox`, while `codex review --help` doesn't list `--model` but does offer configuration overrides.

For a workflow that expects MCP tool calls, a third-party bridge such as [claude-codex-bridge](https://github.com/Dunqing/claude-codex-bridge) is a third approach. Its README says `npx claude-codex-bridge setup` registers both directions and installs a skill and an agent. We read its source on November 26, 2026 but haven't run the bridge: the Codex server starts `codex exec`, including `exec resume` for subsequent turns, instead of `codex mcp-server`, and the latest commit at that date was February 11, 2026. We'd choose it when an existing workflow needs MCP calls and the team is ready to maintain the bridge as the CLIs change.

For an integration that needs authentication, conversation history, approvals or streamed events, OpenAI points to the Codex app server. It speaks JSON-RPC rather than MCP, so existing MCP clients need changes. OpenAI marks the command experimental and unsupported for production workloads.

| What you want | Option | Trade-off |
| --- | --- | --- |
| Ask Codex to review from Claude Code | Official plugin | An explicit call inside Claude Code, not an MCP tool |
| Control a scripted Codex run | `codex exec` or `codex review` | You manage the command and its output |
| Connect a workflow that needs MCP tools | A third-party bridge | You own its setup and version compatibility |
| Let people and separate bots work in a visible conversation | A shared channel such as Alook | Bots participate in chat; their connected computers must stay online |

Teammates and separate bots who share one visible conversation are covered in [Bring Claude Code, Codex, and Humans Together](#bring-claude-code-codex-and-humans-together).

## When one coding agent is enough

You probably don't need a cross-tool workflow when:

- one runtime and one session can finish the task;
- you are still learning either tool;
- native subagents or threads already cover the workflow;
- implementation and review rarely cross between products; or
- copying a short handoff is occasional, not recurring work.

Start with a single agent or a quick manual note. We'd bring in a shared workflow once you catch yourself relaying updates by hand or re-explaining decisions.

Still picking your first coding agent? Our [Claude Code vs Codex comparison](/blog/claude-code-vs-codex) walks through patch review, permissions, and plan allowances. For an editor-centered workflow, see [Cursor vs Claude Code](/blog/cursor-vs-claude-code).

## Keep recurring Claude Code and Codex work on track

Having both apps open doesn't coordinate them. When work passes back and forth, someone has to say what's finished and whose turn it is.

**When a handoff note and the repo disagree, trust the current checkout and test results.** Git history shows committed code, but the working tree may hold newer uncommitted work. Use the handoff note for decisions, open questions, and next steps, then check the project files before continuing.

## Claude Code and Codex FAQ

### How do you use Claude Code and Codex together?

Give each agent a scoped role and isolate concurrent edits. Use Git for code changes, and send an explicit handoff when work moves from one agent to the other. A person keeps final merge and release approval.

### Can Claude Code and Codex work on the same repository?

Yes. If both edit at the same time, give each its own checkout and branch, so they don't write into the same working directory. A Git worktree, a separate clone, or a container with its own repository checkout will keep them apart.

### Can Claude Code delegate to Codex?

Yes. With OpenAI's official plugin, Claude Code can request a Codex review or delegate a task. Give it a clear goal and review target, and check what comes back before you move on.

### Can Claude Code and Codex talk to each other directly?

Claude Code can call Codex through the official plugin, but that's an explicit call, not automatic two-way sharing of every private chat. For separate agents and their owners, someone can pass updates along by hand, or a shared workspace can hold the messages they choose to send.

### Do I need Git or worktrees?

Not for non-code work. If both agents edit the same repository at once, give them separate checkouts and branches so neither overwrites the other's files.

### What happens when a coding-agent session closes?

You can resume a saved session, and the plugin can also transfer a session to Codex, though neither gives every new agent all of the prior private history. Save the current files or make a commit, along with a handoff note. Before you pick the work back up, check the checkout, including uncommitted changes, and read the key decisions.

### Does Alook replace Claude Code or Codex?

No. Alook gives your local bots persistent identities, conversations with teammates, and saved context they can use when work continues. Claude Code and Codex still run commands and edit files, using their owners' configured tools. Teammates can work with those bots directly as long as their computers stay connected.

### What happened to `codex mcp-server`?

OpenAI removed the old server command and the standalone binary. For a Claude Code review, use the official Codex plugin. To manage Codex's connections to external MCP tools, use `codex mcp`.

### Is Alook an MCP server?

No. Alook puts people and their agents in shared conversations, and each agent keeps its own local runtime context and configured tools.
