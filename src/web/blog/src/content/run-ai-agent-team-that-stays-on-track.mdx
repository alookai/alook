One agent is working from your updated plan. Another is still executing yesterday's version. Each one can turn out sensible-looking work while pulling the project in two opposite directions.

Telling the team to “stay focused” doesn't fix that. The real problem is active work still building on an outdated decision. Until every affected agent switches over, updating a plan doc on its own won't stop the wrong output from shipping.

Starting with a clear [brief for the agent](/blog/how-to-delegate-tasks-to-ai-agents) sets the direction up front. Once multiple agents are mid-flight, any change in direction has to reach the runs already in progress.

## When should a human step in to redirect an AI agent team?

You don't need to watch every message to spot drift. Maybe an agent quotes a plan you already scrapped, edits files outside its scope, or starts rewriting code another agent owns. Step in right there, before a handoff turns that mistake into the next agent's starting input.

In practice, human in the loop AI means a person steps in to settle conflicting directions when existing instructions fall short, while letting routine work run uninterrupted.

Check in at natural handoff points, like a first draft or an initial diff, before downstream agents build on top of it. Check again whenever the goal itself changes. Match your attention to the blast radius rather than polling on a timer: a reversible research note needs far less oversight than a script touching production.

Keep authority clear, too. Any teammate can flag a bug or drop a missing fact into the thread, while actual goal changes come from whoever owns the task. Without a clear decision-maker, bots end up treating whichever message arrived last as the new plan.

## How to pause AI agents without losing good work

If an agent keeps expanding a draft built on a bad assumption while you investigate, cleanup only gets harder. Pause that draft and any downstream tasks waiting on it, while letting unrelated work like background source gathering continue.

Typing “hold on” in chat won't stop a tool call that is already running. Hit stop or interrupt in the runtime itself, and verify the process actually halted before touching the files. Background jobs or separate workers often need to be stopped individually. Confirming nothing is still writing matters much more than getting a polite “understood” in chat.

Once the run stops, check two things: what did the agent already change, and what was it about to do next? That tells you how far the mistake spread. Be careful not to mistake half-finished work on another bot for broken work, either; an in-progress branch isn't a signal for a second agent to jump in and overwrite it.

Save the good work completed before the wrong turn. In code, inspect the diff and stash or commit a backup ref before cleaning up. In research or writing, go back to the last solid draft and note which decision it followed. Throwing the whole session away wastes everything that worked.

Every pause also needs a clear owner to resolve it. Name who will answer the open question so the team knows whether to resume or restart once they weigh in. And remember that stopping an agent only prevents the next step; if it already sent a message or published a change, you still have to handle that separately.

## Correct, roll back, or restart: choosing a repair for the team

Where you first notice a bad output isn't always where the mistake started. Often the drift began several steps back, when a rough guess hardened into a fact or a temporary workaround turned into a permanent rule.

Trace back to the last decision that still holds up and see what went sideways after it. Did the goal shift? Did the agent read stale context? Or did it have the right goal and botch one step? Your repair depends on which one happened.

Keep solid work whenever you can; there's no prize for redoing good code just to have a tidy chat log. Still, if every new prompt turns into an argument with the session's original assumptions, starting a fresh session is usually faster and easier to verify. Pass the fresh run the valid inputs, the updated goal, and the old conclusion it should ignore.

Watch the difference between rewinding chat history, restarting a task, and reverting files on disk. In Claude Code, for instance, you can rewind the conversation while leaving working tree edits untouched, and file rollback has specific limits covered in the [checkpoint documentation](https://code.claude.com/docs/en/checkpointing). Before reverting shared files, make sure teammates' or other bots' edits are backed up first. A rewound chat window doesn't mean shared files on disk are untouched.

## How to send new instructions to running AI agents

Editing a plan file on disk doesn't update an agent that already read the old version ten minutes ago. Updating the source of truth and delivering the change to active sessions are two separate steps.

Both bots need the new decision. The writer also needs the corrected sources before revising the draft. [View original image](/blog/run-ai-agent-team-that-stays-on-track/decision-delivery.webp)

Put the updated decision somewhere everyone on the task can read it, noting what it replaces and which existing outputs still stand. Then send that update directly into the active session of each agent still running on the old assumption. If an agent is mid-execution and the change can't wait, interrupt the run first; a queued message won't stop a command that's already executing.

Ask the agent to state its next step rather than just saying “got it.” “Received” only proves delivery, whereas “I'll swap in the revised source list and rewrite the comparison table” shows it understood the change. Remember downstream handoffs, too: correcting a research bot doesn't fix a draft it already passed to a writing bot unless you notify the writer as well.

In Alook, teammates and bots running on Claude Code, Cursor, or Codex share the same channel or thread. Everyone with access to that conversation sees the updated decision alongside the latest files and drafts, so you can @mention the affected bots in one place and read their responses right underneath. That keeps [multi agent collaboration](https://alook.ai/) from turning into one human copy-pasting updates across four terminal windows.

Permissions stay clear in shared threads as well: the goal owner sets direction, and another teammate sharing a helpful fact doesn't automatically gain authority to redirect someone else's bot.

For repeatable workflows, [planning how agents coordinate](/blog/ai-agent-orchestration) covers how to structure handoffs ahead of time. Even with good routing, mid-flight plan changes still have to be pushed to the agents actively doing the work.

## Why do AI agents repeat mistakes after a correction?

Separate one-off fixes from standing rules. “Use this updated source list” only applies to today's task; putting it into global project memory just clutters future sessions.

Save persistent rules for recurring failure modes, and write them as concrete checks. If an agent keeps citing search snippets without reading the linked page, “open every source and confirm it backs the claim before citing it” works much better than “be more careful with research.”

When you add a standing rule, delete or update any older instruction it replaces. Leaving two contradictory lines in `AGENTS.md` or `CLAUDE.md` forces the next session to guess which one wins. Someone should prune those files as workflows evolve, because an outdated approval rule will block valid work just as reliably as it once stopped mistakes.

If an agent ignores a correction, check delivery and conflicts before rewriting the prompt in all caps. Did the running session actually load the updated file, or is an older rule overriding it? Stronger wording won't fix a stale context window. Our guide to [carrying decisions across coding sessions](/blog/keep-context-across-coding-agent-sessions) explains where to keep durable rules versus task handoffs.

Hard boundaries belong in enforcement, not prose. A line in a markdown file advises the model; tool permissions, CI gates, and hooks actually block forbidden actions, as Claude Code's [memory guidance](https://code.claude.com/docs/en/memory) notes. When an action must never happen, enforce it in tooling rather than hoping a prompt reminder holds.

## How to check that an AI agent followed a correction

A correction hasn't landed until the next output reflects it. Editing a rules file, starting a clean session, and getting a confident “will do” are all just setup.

Match your check to the original mistake. If the problem was a stale source list, inspect the citations in the revised output; agents routinely repeat your new rule back to you and still generate a table from cached notes. If an agent edited files outside its scope, check the new diff to confirm unrelated files are untouched. If one bot overwrote another's changes, verify the lost work is restored and has a clear owner again. Focus on proving the specific failure is gone rather than running busywork checks.

Watch out for stale copies sitting in downstream tasks, too. Even after a draft is fixed, another person or bot may still have the old version open. Post a link to the replacement directly in the main thread so everyone knows which file is live and which one is dead.

Five quick lines are enough to close the loop:

- **Decision and owner:** what changed, and who approved it.
- **Affected work:** what was paused and what can continue.
- **Valid material:** existing files, drafts, and findings safe to keep using.
- **Recipients:** every bot or teammate that needs the update before moving on.
- **Result:** the updated output plus the check proving the fix stuck.

Anyone picking up the thread next can immediately see the active decision and the proof that the team is back on track.
