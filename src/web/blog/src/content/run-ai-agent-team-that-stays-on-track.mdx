One agent is working from the new decision. Another is still carrying out the old one. Both can produce reasonable results, and the team can still be heading in two directions.

At that point, another reminder to “stay focused” gives neither agent much to work with. The immediate problem is the work still being built on that decision. Until the affected agents change course, even a corrected plan can leave the team producing the wrong thing.

A clear [brief for the agent](/blog/how-to-delegate-tasks-to-ai-agents) helps at the start. Once several agents are already working, a changed decision has to reach the work in progress, too.

## When should a human step in to redirect an AI agent team?

You don't have to read every message to spot this split. An agent may cite a plan you replaced, deliver something outside the agreed scope, or start rewriting work another agent still owns. Those are reasons to intervene before the next handoff turns the mistake into somebody else's starting point.

When two agents are following different decisions, human in the loop AI means having a person settle which one applies before they continue. The team can keep doing routine work under its existing instructions; a person steps in when those instructions no longer give it a clear answer.

The first draft or working change gives you something to judge before another agent builds on it. A changed goal is another reason to look again. A short, reversible research task needs a different level of attention from a task that can change production. What the next action could affect is a better guide than checking every few minutes by habit.

A teammate may spot an error and supply the missing fact; a change to the goal belongs to whoever has authority over that goal. Without an agreed person to settle changes, the latest message can become the plan simply because it arrived last.

## How to pause AI agents without losing good work

A draft based on a rejected conclusion can keep growing while someone investigates the error. More output makes the repair larger. The useful pause is around that draft and anything about to use it; unrelated source gathering may still be worth continuing.

A pause message alone isn't enough for work already in progress. Use the stop or interrupt control in the tool running the work, then confirm that the affected action has stopped before repairing it. A job running separately may need to be stopped separately. Knowing what is still active matters more here than receiving a polite acknowledgment.

After it stops, what has the agent already made, and what was it about to do? Those answers show how far the error has traveled. Another agent may still be working on something that looks wrong simply because it isn't finished. An incomplete result is not an invitation for a second agent to replace it.

We want to keep the good work on the near side of the mistake. In a repository, that means looking at the changes and saving a recoverable version before repairing them. For research or writing, the useful starting point is the last sound draft or report, together with the decision it followed. Wiping everything loses that distinction.

A pause also needs a clear reason to end. Someone needs to answer the question that stopped the work, and the team needs to know who that is. Their answer will determine whether the agent can continue or needs a new start. Anything already sent or published has to be dealt with separately: stopping the next action doesn't undo the previous one.

## Correct, roll back, or restart: choosing a repair for the team

The latest bad result is where the problem became visible. It may have begun earlier, when a tentative finding became an accepted fact or a temporary restriction became a permanent rule.

The last decision you can still support gives you a place to start looking. What changed after that? Did the goal change? Was the agent using information you'd already replaced? Did it understand the goal but carry out one step incorrectly? Each answer points to a different repair.

A usable result is worth keeping. There's no need to redo it just to get a clean conversation. Once you are spending every message arguing against the session's original premise, though, a new start can be easier to inspect. The next run needs the correct starting point, including which earlier conclusion to leave behind.

Starting a session, restarting a task, and restoring files do different things. In Claude Code, for example, you can restore a conversation while leaving the code as it is. File recovery has its own limits, covered in the [checkpoint documentation](https://code.claude.com/docs/en/checkpointing). Before restoring shared files, other contributors' changes need to be saved somewhere recoverable. A clean-looking conversation is not evidence that their work is safe.

## How to send new instructions to running AI agents

A corrected plan on disk can coexist with an agent still following the version it read earlier. Updating the record and delivering the correction are separate jobs.

![The owner notifies both bots of decision v2. Bot A corrects the sources and sends them to Bot B, which revises the draft before the new result is checked.](/blog/run-ai-agent-team-that-stays-on-track/decision-delivery.webp)

Both bots need the new decision. The writer also needs the corrected sources before revising the draft. [View original image](/blog/run-ai-agent-team-that-stays-on-track/decision-delivery.webp)

Everyone working on the task needs a place to find the current decision, along with what it replaces and which work is still useful. The agents following the old version also need the change sent to the conversation or tool they're working in. A message waiting for a later turn can't stop an action happening now. When the change can't wait, the affected work needs to stop before the new instructions go out.

What the agent plans to do next tells you more than an acknowledgment. “Received” tells you the message arrived. “I will use the revised source list and replace the unsupported comparison” gives you something to check. And a corrected researcher doesn’t automatically repair the draft already handed to a writer. The writer needs the change, too.

In Alook, people and bots running through Claude Code, Cursor, or Codex can take part in the same discussion. The people and bots allowed into that discussion can see the new decision and the drafts or files shared with it. You can address the affected bots there and keep their replies beside the correction. That makes [multi agent collaboration](https://alook.ai/) less dependent on one person repeating the same update in separate terminals.

The person responsible for the goal can settle the change in that discussion. Someone else supplying a missing fact doesn't, by itself, give them permission to direct another person's bot.

For recurring work, [planning how agents coordinate](/blog/ai-agent-orchestration) covers who passes work to whom ahead of time. A changed decision still needs to reach the agents already in the middle of that work.

## Why do AI agents repeat mistakes after a correction?

Some corrections belong only to the current task. “Use this revised source list” should replace an input for this job. It doesn't need to become a rule for every future session.

Other corrections describe a repeatable failure. If an agent keeps treating a search summary as a verified source, a rule can name the check: open the source and confirm it supports the claim before using it. That is easier to apply and verify than “be more careful with research.”

A new rule can leave an older, conflicting instruction in place. Keeping both leaves the next agent to choose between them. Reusable instructions need an owner who revisits them when the workflow changes or the same failure comes back. A rule written for an old approval process can block today's authorized work just as effectively as it once prevented a mistake.

When a correction doesn't stick, did the agent receive it at all? It may still be working from an older set of instructions. Or the new rule may conflict with one that's still in place. Adding a stronger adjective to the same reminder will not resolve those problems. The guide to [carrying decisions across coding sessions](/blog/keep-context-across-coding-agent-sessions) covers where durable instructions and handoff records belong.

Some limits need to stop an action, even when the model decides it should go ahead. Writing a sentence in a file won't do that on its own. In Claude Code, written instructions guide the model, while a hook can block an action, as its [memory guidance](https://code.claude.com/docs/en/memory) explains. Permissions and required checks are worth using when a reminder isn't enough.

## How to check that an AI agent followed a correction

The correction is done when the next result follows the new decision. A revised rules file, a fresh session, or a confident acknowledgment is an intermediate step.

For a stale source list, the evidence is in the sources used by the new result. An agent can repeat the corrected instruction perfectly and still hand over a comparison built from the old material. That is the gap this check needs to catch.

When an agent has changed more than it was asked to, the revised files or draft show whether it now does only what was agreed. After one agent overwrites another's work, the missing contribution needs to be back in place, with someone clearly responsible for continuing it. The original failure tells you where to look. Repeating unrelated checks just to appear thorough adds little.

Even a repaired draft can leave an old copy in someone else's task. The next person needs to know which version to use and which one to put aside. A link in the original discussion keeps that decision beside the work, instead of leaving someone to reconstruct it from scattered messages.

A short record is enough to carry this forward:

- **Decision and owner:** what applies now, and who settled it.
- **Affected work:** what paused and what can resume.
- **Valid material:** the drafts, files, and findings still worth using.
- **Recipients:** who needs the correction before continuing.
- **Result:** the new draft or files and the check that shows the correction worked.

The next agent can then see which decision applies to its work, and the result that shows the team is following it.
