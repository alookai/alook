You run Claude Code in one terminal and Codex in another. Codex finishes reviewing a patch. You copy its notes into Claude Code, explain which commit they apply to, and carry the updated diff back to Codex for a second pass. You have turned into a human clipboard.

AI agent communication is how agents pass goals, inputs, status updates, and results to each other. An agent-to-agent protocol gives separate systems a standard way to exchange that work, and Agent2Agent (A2A) is one open standard built for it.

Pick your communication path based on what you actually need to send: a saved file, a tool call, a delegated task, or a decision your team needs to follow.

## What does agent-to-agent communication carry?

Take a simple patch review: the sender passes a diff and the matching rules to check, and the reviewer replies with findings or asks for missing context.

Five distinct layers can carry that kind of exchange:

<div className="max-w-full overflow-x-auto thin-scrollbar">
<div style={{ minWidth: "640px" }}>

| Layer | What it carries | What you need to check |
|---|---|---|
| Native runtime messages | Instructions and results within a runtime's supported agent system | Which workers can communicate and what survives a session |
| Shared artifacts | Patches, documents, test logs, and other saved outputs | Access, version, and how the recipient learns they are ready |
| MCP | Requests to exposed tools and context sources | Client/server support and any optional extensions |
| A2A | Messages, task state, and outputs between compatible agents | Supported interfaces, authorization, and output retention |
| Shared workspace | Contributions, attachments, discussion, and explicit next steps | Audience, attention, and who has agreed to act |

</div>
</div>

In practice, teams mix these layers. A saved patch file can come back as the output of a remote task and then sit inside a group chat where people debate the fix.

## What is the Agent-to-Agent (A2A) Protocol?

A2A is an open protocol that lets independent agents discover each other and exchange messages, tasks, and outputs. A client sends work through the remote agent's public interface while the remote agent keeps its internal tools, prompts, and implementation private. You can read how that boundary works in the [A2A core concepts](https://a2a-protocol.org/latest/topics/key-concepts/).

### Why A2A was created

Google [introduced A2A on April 9, 2025](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/) so agents built on different frameworks or run by different vendors could pass work across boundaries without exposing their internals.

### Agent Cards: how agents discover capabilities

An Agent Card publishes an agent's identity, skills, supported interfaces, and auth requirements. A calling client reads the card first to decide whether that remote agent fits the job.

Before sending a patch out for review, for example, the client checks the card for a code-review skill, a compatible transport, and required credentials. Discovering the reviewer is only step one; you still have to verify the returned findings against the code.

The [official discovery guide](https://a2a-protocol.org/latest/topics/agent-discovery/) covers several ways to fetch cards, including well-known URLs, registries, and static config. Internal company setups often point clients directly at known endpoints via static config.

### How A2A works: messages, tasks, and artifacts

Walk through a request to review a patch that changes how duplicate contacts get merged.

![A2A flow: discover an Agent Card, send a Message, then receive either an immediate Message reply or a tracked Task that returns Artifacts.](/blog/ai-agent-communication/a2a-message-task-flow.webp)

*A2A can return an immediate Message or track work as a Task with output Artifacts.*

As the [task lifecycle guide](https://a2a-protocol.org/latest/topics/life-of-a-task/) explains, quick exchanges can return a direct Message, while longer jobs run as stateful Tasks. If the reviewer gets stuck because it needs to know your duplicate-matching rule, the Task enters an input-required state and asks before continuing.

Messages carry the back-and-forth conversation, while Artifacts hold concrete deliverables like the finished review report. Watch out for one detail in [A2A v1.0.0, section 3.7](https://a2a-protocol.org/v1.0.0/specification/#37-messages-and-artifacts): clients cannot assume every informational Message stays in task history forever. Persist any outputs your application needs to keep.

If you want to spin up a test agent in code, start with the [official Python quickstart](https://a2a-protocol.org/latest/tutorials/python/1-introduction/), which walks through a minimal echo server. The diagram above focuses on how the protocol objects fit together rather than SDK boilerplate.

## A2A vs MCP: what each protocol handles

MCP wires an AI application to tools and data sources, whereas A2A lets separate agents discover each other and hand off work. Developers mix the two up constantly: in a [December 2025 post](https://x.com/pamelafox/status/2001411044955295972), Microsoft developer advocate Pamela Fox noted that A2A versus MCP is one of the questions she hears most in office hours.

Looking at what you ask the other side to do makes the split obvious:

<div className="max-w-full overflow-x-auto thin-scrollbar">
<div style={{ minWidth: "640px" }}>

| Question | MCP | A2A |
|---|---|---|
| What am I connecting to? | A server exposing context or capabilities to an AI application | An independent agent exposing an agent interaction interface |
| What might I request? | Read a resource or invoke a tool | Send work, answer a clarification, or retrieve a task |
| How is longer work handled? | Optional Tasks support, where both sides implement it | The protocol's Task model and supported update mechanisms |

</div>
</div>

That breakdown matches how the spec authors position both standards in the [official A2A and MCP comparison](https://a2a-protocol.org/latest/topics/a2a-and-mcp/).

<span id="is-mcp-an-agent-to-agent-protocol" />

### Can MCP be used for agent-to-agent communication?

Yes. Nothing stops you from wrapping an agent behind an MCP tool. A `review_patch` tool on an MCP server might spin up a specialist agent under the hood, while the caller simply invokes a tool with structured inputs and reads the tool result.

More broadly, MCP defines how hosts talk to servers exposing tools, resources, and prompts, regardless of whether those servers run plain code or an LLM loop internally. See the [MCP 2026-07-28 specification](https://modelcontextprotocol.io/specification/2026-07-28/) for the full model.

MCP isn't limited to fast synchronous calls either. Its optional [Tasks extension](https://modelcontextprotocol.io/extensions/tasks/overview) adds task handles and status polling for long-running work, provided both your MCP client and server implement that extension.

### How A2A and MCP work together

Going back to the patch review: your coding agent might call an MCP tool to pull a git diff and test log, then send that bundle over A2A to an independent security-review agent. That remote reviewer can in turn call its own private MCP tools to inspect dependencies before sending back an Artifact.

In short, MCP gives an agent hands to reach tools and data, while A2A carries delegated work between separate agents. Above both, a client UI or shared workspace shows people what happened.

## When do you need A2A, and when is a simpler approach enough?

For a quick one-off code review, dropping a patch file in a shared folder with a clear prompt works fine. A2A starts paying off when independent services need a standard contract to discover remote agents and track async tasks.

### When an agent-to-agent protocol helps

Suppose several internal apps all want to send diffs to a central review agent maintained by another team. Each caller needs a predictable way to authenticate, submit inputs, answer follow-up questions, and fetch the final report.

Giving that review service an A2A interface lets every caller reuse the same client logic and task states. Keep the operational cost in mind, though: someone still has to host the service, manage auth, and keep protocol versions compatible.

### When native messages or shared files are enough

If both workers already live inside the same agent runtime, built-in subagent delegation usually handles the handoff with zero extra plumbing.

Even across two separate tools, occasional handoffs often need nothing fancier than a versioned file and an explicit message. Make sure the second agent can read the file path, tell it clearly what to check, and ask it to confirm receipt so work doesn't silently stall.

Before adopting A2A, ask four questions:

- Can the receiving agent already do the job through native subagents or shared files?
- Do you actually need dynamic capability discovery and remote task state?
- Do both systems support the same A2A version and features?
- Who owns auth, retries, and artifact storage in production?

Notice that system boundaries matter more than team size here. A solo developer calling external vendor agents might benefit from A2A, while a fifty-person engineering org might happily pass specs and patches through Git and shared channels.

### Three ways to pass work between Claude Code and Codex

In day-to-day coding, you have three practical ways to bridge two local runtimes:

<div className="max-w-full overflow-x-auto thin-scrollbar">
<div style={{ minWidth: "640px" }}>

| Approach | What you do | Cost to account for |
|---|---|---|
| Copy the request and answer yourself | Paste the review brief into Codex, then bring its findings back to Claude Code | You repeat the delivery and must keep revision details accurate |
| Shared files plus an explicit request | Save the patch, brief, and review report where both tools can read them; tell the recipient which version is ready | You manage access and file versions, and still need acknowledgment |
| A configured messaging service or agent interface | Connect both participants to a service that carries requests and results | You configure access and runtime support, then check how delivery and failures are reported |

</div>
</div>

Copy-pasting a short prompt is totally fine when you do it once. Once a patch goes through two or three review rounds, writing patches and findings to versioned files keeps everyone straight on which commit was checked. Connecting both runtimes to a shared messaging channel removes the manual relay altogether, though you still need clear instructions so each bot knows its role.

### What to include in an agent handoff

A good handoff states five things: the goal, the current artifact and test output, the files involved, any open questions, and what the receiver is allowed to do next. Keep it tight:

```text
Review the duplicate-contact patch at the supplied commit.
Inputs: patch, matching rules, and test output attached.
Check: two records with different casing in the email field.
Open question: should archived contacts count as duplicates?
Next action: report findings. Do not merge or change production data.
```

That five-line brief tells the reviewing agent exactly where to look and flags the product question waiting on a human. If you already tried an approach that failed, mention it so the next agent doesn't repeat the dead end. ## Keep agent communication visible to people

### Track completion, blockers, and the next owner

A protocol call can return `200 OK` and a finished Task while the engineering change itself is still blocked on a product call. Someone has to read the review report, spot the blocker, and claim the follow-up.

Distinct status updates keep work from falling through the cracks. "Request sent" just means the message left your outbox, while "review accepted" confirms an agent picked it up. When the reviewer comes back with "review complete, duplicate rule unresolved," the human owner knows it is their turn to make a call.

Raw protocol logs rarely give teams a comfortable place to make those calls. Putting the review artifact inside a shared workspace lets people read the findings, answer the open question, and assign the next pass in one thread. For patterns around routing and retries, see [orchestrating agent execution](/blog/ai-agent-orchestration).

## Frequently asked questions about agent-to-agent communication

<span id="do-ai-agents-share-memory-when-they-communicate" />

### Do agents share memory when they communicate?

No. Communicating agents pass chosen inputs and outputs without automatically sharing private memory. Each request or artifact carries only the context the sender includes, though the receiving agent can also read any files or services it already has permission to open.

### Does A2A preserve every agent message?

No. A2A v1.0.0 separates task outputs (Artifacts) from informational Messages, and a task history does not have to retain every Message. Decide upfront how you will store important outputs instead of treating an A2A exchange as a permanent log.

### Do coding agents in separate terminals communicate automatically?

No. Opening two terminals side by side does not link the agents inside them. Passing requests and results requires an explicit path, such as shared files paired with a clear prompt, or a messaging service connected to both runtimes.

### Can my agent communicate with a teammate's agent?

Yes, once both agents connect to a shared messaging service or compatible agent interface and both owners permit the interaction. If the agents run on separate machines, the receiving agent also needs access to any referenced files, such as through a shared attachment or repository.
