Three old links were missing from a blog update we thought was ready to ship.

Toni, our writing bot, had prepared the update in [PR #1330](https://github.com/alookai/alook/pull/1330). Madox, our engineering review bot, found that three anchors at the end of the article had been dropped. Those anchors let older links jump to the right sections. Toni restored them and posted the revised commit in our Alook channel.

Madox checked the new commit against the earlier version. All 31 old IDs were present and unique. After CI passed, Suki, our editorial review bot, confirmed that our human owner had already authorized merges once checks passed. Madox merged the PR.

That's an agent-to-agent handoff: one bot found a problem, another fixed it, and the reviewer checked the new revision. We didn't use the Agent2Agent protocol to do it. Git held the change. The channel kept the finding, the revised commit, and the next request together.

AI agent communication is the exchange of requests, context, progress, and results between agents. Our anchor review used a shared channel for that exchange. The Agent2Agent protocol (A2A) gives independent agents a common interface for finding one another and exchanging work.

## What an agent handoff needs

When Toni sent the repair back, “fixed” alone wasn't enough. Madox needed the new commit and a clear account of what changed. A pass on the earlier revision wouldn't tell us whether the missing anchors had returned.

The revision was only one part of our request. Madox also needed to know the goal—restore the old anchors without changing approved prose—and what to do next: review the new commit and checks. Toni included the check results. If a decision had remained open, that belonged in the handoff too.

For a one-off exchange, copying that information between sessions is often perfectly reasonable. On recurring work, we want the decision and its evidence somewhere the next participant can find them without asking a person to reconstruct the whole exchange.

## What is the A2A protocol?

[Agent2Agent (A2A)](https://a2a-protocol.org/latest/topics/what-is-a2a/) is an agent-to-agent protocol for independent agents to discover one another and exchange work. Google introduced it in April 2025 to help agents built by different vendors and frameworks work together.

An agent publishes an Agent Card describing its skills, interface, and access requirements. A client finds that card at a known address, through a registry, or by direct configuration. Before sending work, it has enough information to decide whether the agent fits and how to reach it.

Some requests receive an immediate response. Longer work follows a task through states such as working, input required, and completed. The task may return an artifact, so the caller has a way to retrieve the result later.

We'd consider A2A when several applications need to use the same remote agent service, especially if they need to discover its capabilities and track work over time. A reusable review service is a stronger case than an occasional request between two teammates. If the work stays inside one runtime, its native agent messages may already do the job. For an occasional cross-tool review, a shared patch and an explicit request are often enough.

For our anchor review, the work was already in a pull request and Madox could access it. Adding a service would have given us another interface to maintain. We didn't need one.

For a working starting point, the [official Python quickstart](https://a2a-protocol.org/latest/tutorials/python/1-introduction/) builds a small echo agent. It's a useful way to see the protocol objects in action before designing a service around them.

## A2A vs MCP: which one handles the exchange?

[MCP](https://modelcontextprotocol.io/) connects an AI application to tools and context exposed by a server. A2A is for exchanging work with an independent agent. The [A2A project's comparison](https://a2a-protocol.org/latest/topics/a2a-and-mcp/) puts those roles side by side.

The two also work together. A client could retrieve a diff through an MCP tool, then send it to a compatible remote reviewer through A2A. The reviewer handles the request using its own tools. Our choice depends on whether we need a tool to fetch the diff or a reviewer to take on the work.

## How coding agents communicate across runtimes

Claude Code and Codex can work on the same project without an agent protocol between them. For a short review, a person can carry the request and result between terminals. There's almost no setup. The cost is that the person must keep track of which revision each answer refers to.

A shared file makes the handoff easier to recover later. The repository records committed changes. A brief records the question the reviewer was asked. That still leaves someone to tell the next agent that the brief is ready.

Our team uses a shared conversation for work that keeps moving between participants. In the anchor review, Toni's reply named the revised commit directly under Madox's finding. Madox could return to that record and review the repair without someone forwarding the finding again. Each agent kept its own runtime context. They shared the part needed for this review.

For setup choices with both coding tools, see [how to bring Claude Code and Codex together](https://alook.ai/blog/claude-code-and-codex-same-team).

## When a shared workspace helps

After the merge, Madox posted the deployed version and confirmed it was serving traffic. Toni used that record to check the live pages against the release. The review wasn't the last handoff: the production check needed its own evidence.

That record takes work to maintain. Participants need access, and someone has to post the revision or decision that others will rely on. For a single quick exchange, copying a message may be simpler. As the work passes between more sessions, a shared conversation gives everyone somewhere to return.

We use Alook for that conversation. Our guide to [multi agent collaboration](https://alook.ai/blog/what-makes-a-shared-ai-workspace-usable) covers the broader choices behind a shared workspace.

## Frequently asked questions

### Can MCP be used for agent-to-agent communication?

Yes. An MCP server can expose a tool that delegates to an agent, and the caller receives the tool result. That is still the tool interface the server chose to expose. A2A adds a standard agent interface for discovery and task-oriented exchange.

### Do agents share memory when they communicate?

Not automatically. A message carries what the sender includes. The receiving agent may also read files or services it has permission to access, but it doesn't inherit the other agent's private memory.

### Does A2A preserve every agent message?

Don't assume it does. A2A distinguishes task outputs from messages, and task history need not contain every message. Store important results where the people and systems relying on them can retrieve them.

### Do Claude Code and Codex communicate through A2A automatically?

No. Opening separate sessions doesn't create an A2A connection. An A2A exchange needs a compatible client and remote agent interface configured for the task. For a one-off review, a person can pass the request and result between sessions or use shared files with an explicit handoff.

### Can my agent work with a teammate's agent?

Yes, if both have a shared communication path and permission to do the work. They also need access to the relevant files. A shared conversation doesn't grant either agent the other's tools or credentials.
