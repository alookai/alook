You run Claude Code in one terminal and Codex in another. Codex finishes reviewing a patch. You copy its findings back into Claude Code, explain which revision they refer to, then carry the updated patch back for another check. You've become the messenger.

AI agent communication is the exchange of goals, inputs, status, and results between agents. An agent-to-agent protocol gives independent systems a common way to exchange work. Agent2Agent (A2A) is one such protocol.

Choose by what you need to send: a file, a tool request, a task for another agent, or a decision someone needs to see.

## What does agent-to-agent communication carry?

A patch-review request can include the diff and matching rules. The receiver can then return findings or ask for missing input.

The five layers below carry different kinds of work:

<div className="max-w-full overflow-x-auto thin-scrollbar">
<div style={{ minWidth: "640px" }}>

| Layer | What it carries | What you need to check |
|---|---|---|
| Native runtime messages | Instructions and results within a runtime's supported agent system | Which workers can communicate and what survives a session |
| Shared artifacts | Patches, documents, test logs, and other saved outputs | Access, version, and how the recipient learns they are ready |
| MCP | Requests to exposed tools and context sources | Client/server support and any optional extensions |
| A2A | Messages, task state, and outputs between compatible agents | Supported interfaces, authorization, and output retention |
| Shared workspace | Contributions, attachments, discussion, and explicit next steps | Audience, attention, and who has agreed to act |

</div>
</div>

You can combine them. A saved patch can be the output of a remote task and the subject of a discussion in a group chat.

## What is the Agent-to-Agent (A2A) Protocol?

A2A is an open protocol for discovering independent agents and exchanging messages, tasks, and outputs with them. The client sends work through the remote agent's interface while that agent keeps control of its own tools and implementation. The [A2A core concepts](https://a2a-protocol.org/latest/topics/key-concepts/) describe this client-and-remote-agent relationship.

### Why A2A was created

Google [introduced A2A on April 9, 2025](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/) to help agents built with different frameworks or by different vendors interoperate.

### Agent Cards: how agents discover capabilities

An Agent Card describes an agent's identity, skills, interfaces, and access requirements. A client can inspect it before deciding whether to send work.

Before sending a patch for review, the client checks the card for a relevant skill, a compatible interface, and the access requirements. The card helps it find a reviewer; the findings still need to be checked against the patch.

The [official discovery guide](https://a2a-protocol.org/latest/topics/agent-discovery/) describes several ways to obtain cards, including a well-known address, a registry, and direct configuration. Private deployments can use direct configuration to find the intended agent.

### How A2A works: messages, tasks, and artifacts

Consider a request to review a change to duplicate-contact handling.

![A2A flow: discover an Agent Card, send a Message, then receive either an immediate Message reply or a tracked Task that returns Artifacts.](/blog/ai-agent-communication/a2a-message-task-flow.webp)

*A2A can return an immediate Message or track work as a Task with output Artifacts.*

The [task lifecycle guide](https://a2a-protocol.org/latest/topics/life-of-a-task/) distinguishes immediate Message responses from stateful Tasks. If a review needs more input, such as the intended duplicate-matching rule, the Task can request it before the reviewer continues.

Messages carry the conversation; Artifacts carry task outputs. In the example, the review report belongs in an Artifact. Under [A2A v1.0.0, section 3.7](https://a2a-protocol.org/v1.0.0/specification/#37-messages-and-artifacts), clients cannot assume that every informational message will remain in task history. Save important outputs according to the retention requirements of your application.

To build a working agent, use the [official Python quickstart](https://a2a-protocol.org/latest/tutorials/python/1-introduction/), which starts with an echo server. The flow above explains the objects, rather than supplying SDK code.

## A2A vs MCP: what each protocol handles

MCP connects an AI application to tools and context; A2A lets independent agents discover capabilities and exchange work. In a [December 2025 post](https://x.com/pamelafox/status/2001411044955295972), Microsoft developer advocate Pamela Fox described A2A versus MCP as a question she often receives in office hours.

The requested work makes the distinction clearer:

<div className="max-w-full overflow-x-auto thin-scrollbar">
<div style={{ minWidth: "640px" }}>

| Question | MCP | A2A |
|---|---|---|
| What am I connecting to? | A server exposing context or capabilities to an AI application | An independent agent exposing an agent interaction interface |
| What might I request? | Read a resource or invoke a tool | Send work, answer a clarification, or retrieve a task |
| How is longer work handled? | Optional Tasks support, where both sides implement it | The protocol's Task model and supported update mechanisms |

</div>
</div>

This follows the protocols' intended roles, as explained in the [official A2A and MCP comparison](https://a2a-protocol.org/latest/topics/a2a-and-mcp/).

<span id="is-mcp-an-agent-to-agent-protocol" />

### Can MCP be used for agent-to-agent communication?

Yes, an application can expose an agent-backed capability as an MCP tool. A review tool might delegate work to an agent internally. The caller still interacts with the tool interface that the server exposes.

MCP defines a broader integration interface for tools, resources, and prompts. A server can implement its exposed capabilities with ordinary functions or agent workflows. See the [MCP 2026-07-28 specification](https://modelcontextprotocol.io/specification/2026-07-28/).

MCP can handle longer-running work too: its optional [Tasks extension](https://modelcontextprotocol.io/extensions/tasks/overview) supports longer operations through task handles and status retrieval. Check support in your client and server before depending on it.

### How A2A and MCP work together

In the patch-review example, an agent could use an MCP tool to retrieve a diff, then send a review request to a compatible remote agent through A2A. The remote agent could use its own tools to inspect the change.

MCP supplies access to a capability; A2A carries the exchange with the independent reviewer. A client or workspace can display the result to people.

## When do you need A2A, and when is a simpler approach enough?

For a one-off patch review, a shared patch and a clear request may be enough. A2A becomes worth evaluating when you need a standard interface for discovering remote agents and tracking their work.

### When an agent-to-agent protocol helps

A review service used by several applications is a stronger case for A2A. Each caller needs a compatible interface and the required access; the service needs to accept agreed inputs and return usable review outputs.

With a common interface, those applications could reuse the same way to request reviews and track progress. That benefit comes with integration work: someone has to operate the service and maintain compatibility.

### When native messages or shared files are enough

A reviewer inside the same runtime's agent system may already receive requests and return findings through native delegation.

An occasional review by another tool may only need a versioned patch and a short brief. The receiver must be able to access the files, and someone must make the request explicit. Ask the reviewer to confirm acceptance, so you know who has the next action.

Before adding A2A, check:

- Can the recipient act using the existing runtime interface or a shared deliverable?
- Do you need standardized capability discovery and remote task tracking?
- Do both sides support the required protocol version and features?
- Who will maintain access, failures, and retained outputs?

The interface and tracking requirements matter more than head count: one person can use remote agent services, while a large team can exchange useful work through files.

### Three ways to pass work between Claude Code and Codex

You have three options:

<div className="max-w-full overflow-x-auto thin-scrollbar">
<div style={{ minWidth: "640px" }}>

| Approach | What you do | Cost to account for |
|---|---|---|
| Copy the request and answer yourself | Paste the review brief into Codex, then bring its findings back to Claude Code | You repeat the delivery and must keep revision details accurate |
| Shared files plus an explicit request | Save the patch, brief, and review report where both tools can read them; tell the recipient which version is ready | You manage access and file versions, and still need acknowledgment |
| A configured messaging service or agent interface | Connect both participants to a service that carries requests and results | You configure access and runtime support, then check how delivery and failures are reported |

</div>
</div>

Copying a short brief can be a reasonable choice for a single review. Once reviews repeat, saved inputs and findings help you check which revision each answer refers to. With a configured service, the participants can send requests and replies themselves. The review scope still has to be clear.

For the full setup and division of work, see the [Claude Code and Codex workflow](/blog/claude-code-and-codex-same-team).

### What to include in an agent handoff

The receiver needs the objective, current output and evidence, relevant files, unresolved questions, and permitted next action. Keep the brief specific to the job:

```text
Review the duplicate-contact patch at the supplied commit.
Inputs: patch, matching rules, and test output attached.
Check: two records with different casing in the email field.
Open question: should archived contacts count as duplicates?
Next action: report findings. Do not merge or change production data.
```

This brief tells the reviewer where to start and which product decision needs an answer. Include failed attempts when they change what the next agent should try. The [shared-context guide](/blog/shared-context-between-agents) covers the fuller handoff problem.

## Keep agent communication visible to people

### Track completion, blockers, and the next owner

A review service can finish successfully while the patch still needs a decision. The author needs to know whether the report contains a blocker, and someone needs to accept the follow-up.

Each status tells the author something different. "Request sent" means the review is waiting for a response; "review accepted" means someone has taken it on. Later, "review complete, duplicate rule unresolved" tells the author to read the findings and make a decision.

A client can display the protocol events. A shared workspace keeps the selected report beside the discussion, so the author can read the findings and record the next decision in the same place. For execution control, see [orchestrating agent execution](/blog/ai-agent-orchestration).

## Frequently asked questions about agent-to-agent communication

<span id="do-ai-agents-share-memory-when-they-communicate" />

### Do agents share memory when they communicate?

Agents exchange selected information rather than automatically sharing private memory. A request or artifact carries the context the sender includes. The recipient can also use files and services it already has permission to access.

### Does A2A preserve every agent message?

No. A2A v1.0.0 distinguishes task outputs from informational Messages, and task history need not contain every Message. Agree on retention for important outputs rather than treating the interaction as a permanent transcript.

### Do coding agents in separate terminals communicate automatically?

Separate terminals alone do not connect the agents. Requests and results need a supported path, such as shared files with an explicit request or a messaging service connected to both participants.

### Can my agent communicate with a teammate's agent?

Both agents need access to a shared messaging service or compatible agent interface, connected runtimes, and their owners' permission for the work. When agents run on different computers, the receiving agent also needs access to any referenced files. A shared attachment or repository can supply the output when the recipient has access.
