If you start several agents on the same job at once, one often ends up waiting on another's findings or building on a guess. A good workflow lets independent tasks run in parallel while making real dependencies explicit.

Bug reports, releases, and research briefs each take a different path to done. Add another agent only when splitting the work actually helps. A single coding agent can already investigate, edit code, and run tests on its own.

## How should the work move between agents?

### 1. Sequential work: wait for the input you need

When the next step depends on an output that doesn't exist yet, starting early usually means guessing and redoing the work later.

Say one agent is updating a database schema while another builds the UI that reads it. If you lock down the interface first, both can work at the same time. Without an agreed contract, finishing the schema first is usually simpler. You can still write schema changes in parallel, provided someone orders the migrations, resolves conflicts, and tests each change before merge. Our guide to [multiple agents working in one repository](/blog/multiple-ai-agents-edit-same-repository) covers how to isolate branches and manage merge order.

### 2. Parallel work: split independent tasks

When tasks don't depend on each other, run them side by side. For a research brief, one agent can read current product docs while another reviews user bug reports. Neither needs to wait for the other to start.

### 3. Review and revision: return work that fails

Leave room for review to send work back before anyone else builds on it. If a check fails, route the work back to its author for a fix. If people disagree on what counts as passing, get a decision on the rule first.

### 4. Task routing: choose where each item goes

Not every incoming item follows the same path. A known support question can go straight to an answer, while a bug report goes to investigation. Even inside a bug queue, one owner needs to claim each ticket before starting so two agents don't fix the same issue twice.

Real workflows mix these four patterns. In the checkout example below, investigation runs before development, and review can send the patch back if something breaks.

## Worked example: a bug report becomes a PR

Take a hypothetical checkout bug. A cart has a **$100.00 subtotal before tax**, and applying **SAVE10** should subtract **$10.00**. Instead of **$90.00**, the order summary displays **$0.00**. A logged-in user with one paid item hits this in staging. The fix must leave tax calculation, payment capture, and unrelated promo rules untouched.

Investigation, implementation, and review are three distinct jobs here, though you don't need three bots to run them. One agent can investigate and write the patch while a second agent reviews it. The key is independent verification: the reviewer checks the diff and behavior directly instead of taking the author's word for it.

### From investigation to a patch

Implementation starts from the reproduction steps and boundaries produced during investigation. In this example repo, investigation turns up three facts:

- Add `SKU-100`, apply `SAVE10`, and open the order summary to trigger the `$0.00` total.
- Discount order in `src/checkout/coupon.ts` is the likely culprit.
- Staging logs show `coupon.apply amount=null`, and `checkout.coupon.spec.ts` has a failing test case.

Once the failure is reproducible and the likely cause is pinned down, the developer can write the fix. Unrelated work, like a docs update, can run in parallel, whereas writing the patch before investigation finishes would just be guesswork.

The patch is ready for review when the cart shows **$100.00 − $10.00 = $90.00**, a regression test covers the bug, and the test suite passes. Keep the diff focused on the coupon bug. Touching payment capture or refactoring checkout turns a small review into a much riskier one.

### Review can move the work forward or send it back

The reviewer reads the diff, runs the reproduction steps on the branch, and checks the new regression test and its output. Fixing `SAVE10` doesn't count if the patch breaks another coupon rule.

When review catches an issue, route it back to whoever can actually fix it:

- **Can't reproduce the bug:** ask the issue reporter for clearer steps or a recording.
- **Wrong root cause:** send it back to investigation before writing another patch on a bad assumption.
- **Another coupon case breaks:** return the patch to the developer with the failing case.
- **Unclear discount rule:** escalate to whoever owns checkout product decisions.

If a single agent handled both investigation and coding, a bad root cause sends that same agent back to investigate. If two separate agents handled them, send the findings back to the investigator.

After the revised patch passes review, whoever holds merge permission can land it. Any further code edits should re-run the affected checks before merge.

## Six more workflows you can adapt

In the checkout example, coding waits for investigation and review waits for the patch. Other jobs call for different layouts, even with the exact same team of agents.

### Release preparation and documentation changes

Once the release commit range is locked, one agent can draft release notes while another runs compatibility checks. Both read the same changes for different reasons, then sync up before ship: if compatibility review flags a breaking change, the release notes need an update too. And if a late commit lands in the release branch, re-check both outputs against the updated diff before the release owner ships.

Docs updates follow code reality, not early design drafts. An agent can list which doc pages need edits while a feature is still in progress, then test the final CLI examples against the finished build. When an example fails, check with the code author to find out whether the docs or the implementation are wrong instead of blindly rewriting more pages.

### Maintainer queues and incident investigation

Open-source triage starts with routing, not a single pipeline for every ticket. Questions with documented answers can get a draft reply right away, bug reports go to reproduction, and feature requests go straight to a maintainer instead of getting treated like broken code. Once an item is routed, one owner claims it so two agents don't jump on the same issue.

Incident response often fans out in the opposite direction: one alert kicks off multiple parallel checks. One agent inspects recent deploys while another digs through error logs. Compare their findings before acting on a root cause, since two reasonable summaries can still contradict each other.

Pre-approved runbook steps can run immediately while that investigation continues. Anything outside the runbook waits for the on-call owner. Remember that a clean incident summary only helps the team pick the next move; it doesn't mean the outage is resolved.

### Research briefs and customer follow-up

Multiple agents can read separate sources in parallel, as long as someone reconciles their notes before writing a conclusion. Five articles quoting the same press release count as one source, not five independent confirmations. Flag open gaps explicitly in the brief, re-check primary sources when claims conflict, and don't split gathering, deduplicating, and writing across three agents when one agent can do the whole pass cleanly.

Customer follow-ups add an approval boundary on top of research. Someone has to check what a draft reply promises before it goes out. If a draft offers an unapproved pricing discount, stop polishing the copy and ask whoever owns pricing to decide. Routine replies within existing policy can ship as usual, and an agent can finish drafting the message while waiting on that pricing call.
