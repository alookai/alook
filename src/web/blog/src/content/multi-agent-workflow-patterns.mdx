When several agents take on a job, starting them all at once can leave one waiting for another's findings—or building on a guess. A useful workflow lets independent work advance while keeping those dependencies clear.

A bug report, a release, and a research brief need different routes to a usable result. Adding more agents helps only when there is work worth separating; one coding agent can already investigate, edit, and run checks.

## How should the work move between agents?

### 1. Sequential work: wait for the input you need

If the next stage needs a result that doesn't exist yet, starting it early may mean guessing or redoing work.

If an agent is changing a schema while another builds the screen that reads it, agreeing on the interface first can give both something stable to work from. Without that agreement, doing the schema first is often simpler. You can also develop schema changes in parallel, but someone will need to order the migrations, resolve conflicts, and check each change against the code being merged. The guide to [multiple agents working in one repository](/blog/multiple-ai-agents-edit-same-repository) covers how to isolate the changes and handle their merge order.

### 2. Parallel work: split independent tasks

For a research brief, one agent can examine current documentation while another checks independent user reports. Neither needs the other's findings to begin.

### 3. Review and revision: return work that fails

A check may uncover a problem that sends the work back to its author. Allow for that return before the next person starts using the result. A failed result needs a correction, while a disagreement about what counts as success may need a decision first.

### 4. Task routing: choose where each item goes

A support question may go straight to an answer, while a bug report goes to investigation. Sending all bugs to the same queue still leaves a second question: who has taken this particular report? One owner needs to claim it before two agents start the same work.

In the checkout example below, a bug goes to investigation before development begins. Later, review can send the patch back. A workflow can combine these choices; you don't have to choose one arrangement for the whole job.

## Worked example: a bug report becomes a PR

Consider a hypothetical checkout bug: a cart has a **$100.00 subtotal before tax**, and applying **SAVE10** should subtract **$10.00**. Instead of showing **$90.00**, the order summary shows **$0.00**. The issue is reported in staging by a logged-in user with one paid item. The repair must leave tax calculation, payment capture, and unrelated promotion rules alone.

An investigator, a developer, and a reviewer have different responsibilities here. That doesn't require three new bots. One agent could investigate and implement, then a second agent could review. What matters is that the review examines the work rather than simply accepting the author's conclusion.

### From investigation to a patch

The developer starts from the reproduction steps and repair scope established during investigation. In this hypothetical repository, the investigation produces the following:

- Add `SKU-100`, apply `SAVE10`, then open the order summary to reproduce the zero total.
- The suspected area is discount application order in `src/checkout/coupon.ts`.
- A staging log contains `coupon.apply amount=null`, and `checkout.coupon.spec.ts` has a failing case.

With the failure reproduced and the likely cause identified, the developer can work on the coupon fix. An unrelated documentation update can continue separately; starting the patch before those findings are ready would leave the developer guessing.

The patch is ready for review when the original cart shows **$100.00 − $10.00 = $90.00**, a regression test covers the failure, and the relevant checks pass. Its scope should still be the coupon problem. Changing payment capture or refactoring checkout as a whole would give the reviewer a different job from the one the issue described.

### Review can move the work forward or send it back

The reviewer checks the actual diff, repeats the reproduction on the branch, and examines the cited test and its result. If the patch breaks another coupon case, fixing the reported bug isn't enough.

If review finds a problem, send the work back to the person or agent who can resolve it:

- **The bug cannot be reproduced:** return to the issue author for better steps or a recording.
- **The diagnosis points to the wrong code:** return to investigation and revise the explanation before building another fix on it.
- **A different coupon case now fails:** return the patch to its developer with that failing case.
- **The expected discount is a product decision:** return to someone who can decide the rule.

If one agent owns investigation and development, the second path takes it back to investigation. If separate agents own them, the findings go back to the investigator.

Once that revision passes review, whoever is already allowed to merge can take the next step. If the patch changes again, the affected checks may need to run again before it goes further.

## Six more workflows you can adapt

In the checkout example, development waits for the investigation, and review waits for the patch. Other tasks need different arrangements, even when some of the same agents do them.

### Release preparation and documentation changes

Release notes and compatibility checks can happen in parallel once the release scope is fixed. Both are reading the same set of changes for different reasons. They meet again before release: a breaking change found by one reviewer may require the notes to change. If another commit enters the release, the earlier results need to be checked against that new scope. The release owner can then ship the agreed version at the agreed time.

A command example needs to match the behavior that actually lands, not an earlier proposal. An agent can identify affected pages while code is being written, but the final example should be checked against the implementation. If the example fails, the next move is to resolve that mismatch with the relevant author. Rewriting more pages won't settle which behavior is correct.

### Maintainer queues and incident investigation

An open-source queue begins with sorting, not a chain that every item must traverse. A question with an existing answer may go straight to a suggested response; a bug report may need reproduction. After that routing decision, one owner takes the specific item so two agents don't both start it. A roadmap request can reach the maintainer without first being treated as a code defect.

An incident can justify the opposite shape: several investigations start from one alert. One agent checks recent deployments while another looks at logs. Before choosing a repair from a diagnosis, those findings need to be compared: two plausible summaries can still point to conflicting causes. An immediate response already authorized by a runbook can proceed while that investigation continues. An action outside that authority goes to the person responsible for the system. An incident brief can help someone choose the next response; it doesn't mean the incident is over.

### Research briefs and customer follow-up

Different agents can examine separate sources, but the findings need to be compared before they become a single conclusion. Repeated coverage of the same announcement isn't independent confirmation. A contradiction sends the work back to the source in question, while an unresolved gap stays visible in the brief. There's no need to assign collection, deduplication, and writing to three agents if one can handle them well.

A customer follow-up may use that research, but it ends with a different decision. Before a prepared reply goes out, someone needs to check what it promises. If a draft offers a pricing exception that nobody has authorized, the next move is a decision by someone with that authority, not another round of wording changes. Routine messages that already have permission can still go out the usual way. The writer can finish the draft while the pricing decision waits for the person who can make it.

Back at the checkout patch, “in review,” “returned to development,” and “ready for merge” mean different work should happen next. Everyone involved needs to see the patch's current status.
