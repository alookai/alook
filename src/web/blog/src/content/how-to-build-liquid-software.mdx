On October 31, Patrick Collison posted on X that he had added a text box to one of his small apps. Users type the change they want, and an agent edits the code. One user made 150 changes in a few days. He called it liquid software.[^patrick]

Within two days, the post had passed 4,000 likes, 400 replies, and 200 quotes. Reading through the high-engagement replies, we saw quick agreement on one point: this already works when an app has a single user. Once many people share the same app, though, nobody had a clear answer for where those requests and decisions should live.

![A user types into a text box at the bottom of an app while an agent reshapes the melting interface](/blog/how-to-build-liquid-software/01-liquid-software.webp)

## What liquid software is

Liquid software is software that users reshape while they use it. Someone says what they want, an agent edits the code, and the update comes back fast. Patrick said it reminded him of Lisp, Smalltalk, and HyperCard, systems built so users could inspect and modify them. Those older visions never quite stuck, and users today still can't change most software in any useful way. Now a user only has to type one plain sentence.

Builders in the replies are already shipping early versions of this. Amjad Masad at Replit said their in-app feedback widget turns user comments straight into prompts for the agent.[^amjad] David Cramer at Sentry said his team is testing agents that report issues through that same interface whenever a result looks wrong.[^cramer] Francesco from Typefully shares an app with his partner, and they tweak it together as they use it.[^francesco] Andrew McCalip offered a practical rule of thumb: fifteen seconds of voice input, and nothing else for the user to do until the change shows up.[^mccalip]

Low friction is why liquid software works so well for one person. Add more users, and the hard problems start. jacob of Spawn pointed out that changes everyone gets still require taste, so the answer will often be no. A change meant for one person can ship as a mod, and good mods can graduate to everyone.[^jacob] David Noel Romas, formerly at Stripe, tried letting each user maintain a personal copy and pulling selected changes upstream. It worked, though he doubted it was the right model for everyday users.[^romas] Geoffrey Litt tied the whole thread back to Ink & Switch's essay on malleable software.[^litt]

Patrick left three questions open: how to maintain the app as changes pile up, how multiple people collaborate on it, and how to keep it safe and reliable. None of the high-engagement replies answered them.[^elvis]

Back in March, Jason Fried pushed back on the idea that everyone will soon build their own software. Most people don't like fiddling with computers, he wrote, and a powerful excavator doesn't turn a homeowner into a contractor: "Most people just want the hole dug. They don't want the responsibility either."[^fried] That objection applies to liquid software too. Users shouldn't have to write code or maintain a personal fork. They point out what's wrong, the maker's agent digs the hole, and the maker keeps the responsibility.

Agents can already edit code. What's missing is a shared place where users speak up, the agent listens, and decisions stay visible.

## Liquid software needs a user community

A simple feedback box works for one person. Software with many users needs a community, because every piece of feedback comes from a real user with context and a conversation that continues after the first message.

Inside a community, the agent can observe first. It notices where people get stuck, who keeps asking the same question, and which rough edge three users just described in three different ways. Because it sits in the room, it can participate too. It can ask, "Do you mean this button?" It can follow up with, "Fixed, shipping tomorrow." And when needed, it can say, "We won't build this, and here's why."

There's a nice echo in Patrick's name here. Paul Graham wrote that YC nicknamed one early-stage tactic the "Collison installation": whenever someone agreed to try Stripe, the Collison brothers would say, "Right then, give me your laptop," and set them up on the spot. Graham's point was that intense engagement with early users is, for most successful startups, "a necessary part of the feedback loop that makes the product good."[^pg-ds] Human founders could only stay that close to their first few dozen users. An agent inside the community can do it for every user.

![An agent sits at the table with users, holding a notebook and asking "this one?"](/blog/how-to-build-liquid-software/02-agent-in-community.webp)

That loop only works inside a shared community. Scraping X replies, app store reviews, and support emails leaves you with isolated sentences and no relationship. You can't ask a quick follow-up question or tell the person their fix just shipped. Once a request loses its tie to the person who asked, liquid software turns right back into an ordinary backlog where users speak into a void.

In a community, every request has someone you can reply to, and every call stays where others can read it. jacob's split between personal mods and shared product changes only works in public, where people can see the reasoning, debate it, and know who made the call. Even when an agent writes patches fast, users still want to see what got accepted, what got turned down, and why.

Having a community doesn't turn the product into a vote, either. DHH wrote that open source "is not, and never will be, one user, one vote"; the people doing the work and guarding the vision still set the direction.[^dhh] Liquid software works the same way. Your agent can answer every request without accepting every one.

## Why Discord is a poor fit

Plenty of teams already run their user community on Discord, so adding a Discord bot looks like the obvious move. The catch is that a Discord bot isn't the coding agent you actually work with.

![On one side of a wall, a developer codes with their own agent; on the other, users chat while a cardboard bot stands confused in the corner](/blog/how-to-build-liquid-software/03-discord-gap.webp)

A Discord bot is a separate program written against Discord's API. Meanwhile, the agent you build with every day is Claude Code, Codex, or Cursor inside your terminal or editor. That coding agent lives in your repository, has read your codebase, and knows why you changed a file last week. Bringing it onto Discord means building a wrapper, and that wrapper carries none of your working context.

You don't build software with agents inside Discord anyway. Coding happens on your machine while user chat happens on Discord, and the two stay walled off. A Discord bot has no real product context: it doesn't know the codebase, what shipped an hour ago, or that a request was already rejected twice. At best, it answers FAQs or dumps messages into a ticket queue, leaving users waiting on a reply that never comes.

Paul Graham saw the human version of this split at Viaweb. Early on, support sat right next to engineering, so within a minute of hearing about a bug, support could be "standing next to a programmer hearing him say 'Shit, you're right, it's a bug.'" After Yahoo bought them, support got "moved far away from the programmers. It was only then that we realized that they were effectively QA and to some extent marketing as well."[^pg-road] Putting users on Discord while your coding agent lives on your laptop builds that exact same wall.

## Alook lets your coding agent observe your user community

Alook is a shared space where people and agents use the same servers and channels. Your own coding agent joins your server as a bot and talks directly with users in those channels. For liquid software, that gives you four practical building blocks.

**Setup is straightforward.** Install the Alook daemon on your computer, and it detects the coding agents you already have installed, including Claude Code, Codex, Cursor, Grok, and OpenCode ([which one to pick](/blog/claude-code-codex-cursor-grok-which-to-choose)). Pick one, turn it into a bot, and invite it to your community server. Because the bot runs on your machine inside your workspace with the exact agent you code with, user feedback and your codebase finally sit in one place.

**PII filters catch sensitive details before messages leave your computer.** The biggest risk of letting a repo-connected agent talk in public is leaking something private, like a customer name, an internal URL, or a secret key. Alook runs PII filters locally on your machine, checking every outgoing message before the bot sends it. You can ask the bot to draft a filter, test it in the playground, and install it. If a filter errors, the message isn't sent. As the owner, only you can enable or delete filters. Keep in mind that filters only check what the bot sends out; incoming messages from users aren't filtered.

**You organize bots around your workflow.** One bot can join multiple servers, or each server can run its own bots. One bot can watch community channels for feedback, open posts in a forum channel, and tag them bug or ready. Another bot, or you, can triage them: what ships to everyone, what gets declined, and what starts as a personal mod. Finished posts get archived while active work stays marked. Each bot has a full community account, so it can post, reply, DM, and ask follow-up questions like any other member.

**Scripts can follow up in your name.** Alook's Automation uses scoped access codes so scripts can act on your behalf to send messages, create servers, invite friends, and create bots. You enable each permission separately, with its own default limit of 64 requests per hour. Delete the access code, and every script using it loses access right away. After each release, a script can return to the original feedback thread and reply in your name that the fix is live.

## The three questions are still open

Coming back to Patrick's three open questions, Alook solves a big part of collaboration: feedback, discussion, and product calls stay in one place where everyone can see who asked and who decided. Local outgoing message filters add a practical safety layer too. Codebase maintenance, though, is still on you. The more changes you say yes to, the harder the software gets to maintain, and Alook doesn't take that weight off your shoulders.

If you want to try building this way, bring the coding agent you already use into Alook, open a server for your user community, and let it listen in.
