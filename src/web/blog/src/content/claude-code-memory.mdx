**Claude Code includes built-in persistent memory, so test its native notes before reaching for a plugin.** Run the quick three-step check below to make sure memory works in your project.

## Check Claude Code memory in three steps

1. **Save a harmless fact.** In a throwaway project, ask Claude to save a fake review label such as `OPAL-742` in auto memory without modifying your repository instruction files.
2. **Inspect the files on disk.** Run `/memory` and open the auto memory folder. Confirm that both the saved note and its `MEMORY.md` index entry are actually there. Claude saying "I'll remember that" does not prove a file was written.
3. **Ask again in a fresh session.** Quit and run `claude` again in the same project without resume flags. Ask, “What review label should this demo project use?” Leave `OPAL-742` out of your question.

Check Claude's answer against the saved files and any file-read logs your client shows. Seeing the right answer confirms recall, while checking the read log confirms which file Claude actually loaded.

## What does Claude Code remember between sessions?

Claude Code carries project instructions and saved auto-memory notes into new sessions, while session resume picks up an earlier chat where you left off. Pick the option that matches what you want to keep:

| Where it lives | Use it for | What to check |
|---|---|---|
| Instruction files | Standing rules every session in the project should follow | Which instruction files this session actually loaded |
| Auto memory | Useful project notes learned along the way | Whether the note file exists and is readable when needed |
| Session history and resume | Picking up an earlier conversation | Whether you reopened the right session |

### CLAUDE.md and conditional AGENTS.md loading

Put permanent project rules in an instruction file. Notes from earlier experiments or temporary preferences belong in auto memory if they are likely to change.

According to the [official memory documentation](https://code.claude.com/docs/en/memory), `AGENTS.md` loading is conditional: direct support requires v2.1.277 or later, and local `CLAUDE.md` or `CLAUDE.local.md` files affect what loads by default. You can enable both in `/config`, or import `AGENTS.md` through `CLAUDE.md` in older sessions. Check which files are active rather than assuming every instruction file got loaded.

### Where is Claude Code auto memory stored?

The [documented default location](https://code.claude.com/docs/en/memory#storage-location) is `~/.claude/projects/<project>/memory/`, which holds a `MEMORY.md` index alongside separate topic notes. Run `/memory` to confirm the active folder for your session, since custom configuration can move it. Our CLI test below used an isolated config directory, so its `config/projects/...` path is a test folder rather than the default path.

### Session history and resume

Use session resume when you want to continue the conversation itself. The [session guide](https://code.claude.com/docs/en/sessions) covers `claude --continue` for reopening the most recent session in your current directory and `claude --resume` for choosing an earlier one.

When you test cross-session memory, start a brand-new session instead so the old chat history is not supplying the answer.

## Verify memory in a new Claude Code session

Run `/memory` to check that auto memory is turned on, save a test note, and ask for it in a new session. Checking the files on disk and the session's read logs lets you tell whether a problem happened during saving or during recall.

### Use the interactive memory controls

These steps follow the [documented `/memory` controls](https://code.claude.com/docs/en/memory#view-and-edit-with-memory), checked on October 22, 2026. Our hands-on test below ran via CLI calls; the interactive menu steps are documentation-based and were not tested directly here.

Run `claude --version` first and note the build. Launch Claude Code from your terminal inside the project, then:

- Enter `/memory` and check the auto memory toggle. If it is off, turn it on in a directly launched terminal session before testing.
- Choose the option to open the auto memory folder. After your save request, inspect both the topic note and `MEMORY.md`, and check that the actual path and contents match what Claude reported.
- Run `/context` to see which instruction files loaded. That list tells you about instruction files, not whether Claude read an auto-memory topic note.
- Quit, run `claude` again in the same project, and ask your recall question. Check whatever file-read activity your client exposes.

If `/memory` will not let you flip the toggle, restart Claude Code directly from your terminal. Also avoid clicking a missing instruction-file entry in `/memory` just to inspect it, because selecting it can create that file on disk.

### What we tested with the CLI

We tested saving, recalling, updating, and removing memory on macOS with **Claude Code 2.1.304**, the stable build returned by the official download endpoint on **October 21, 2026**.

To keep test notes out of daily work, we ran inside an empty Git repository with a separate `CLAUDE_CONFIG_DIR`. We kept default memory placement with no `autoMemoryDirectory` or `autoMemoryEnabled` overrides. Tools were restricted to Read, Write, and Edit, using project/local settings sources and a strict empty MCP configuration. Those settings narrowed storage and tool access, though machine-level parent instructions were not completely isolated.

Each `-p` call started a fresh conversation without `--continue` or `--resume` (the [CLI reference](https://code.claude.com/docs/en/cli-reference) documents these session and output flags). Rather than taking Claude's chat explanation at face value, we checked the actual tool events and file snapshots on disk.

Claude wrote `demo-review-label.md` and `MEMORY.md` under `config/projects/<encoded-project>/memory/`, adding this index line:

```markdown
- [Demo review label](demo-review-label.md) — demo review label is OPAL-742
```

In the next fresh `-p` call, Claude answered `OPAL-742` and logged a successful read of `demo-review-label.md`. Because both `MEMORY.md` and the topic file contained `OPAL-742`, this run does not prove the topic file was its sole source, though it does confirm Claude read the topic file without any manual index edits.

## Fix Claude Code memory that is not working

When memory fails, check four things in order: where the file was saved, whether `MEMORY.md` points to it, whether you are in the same project scope, and whether the session logged a file read. Fix the first broken step, then retest in a fresh session. If an old value keeps coming back, look for another copy or a conflicting rule in your instruction files.

### Saved files are not being loaded

Open the memory folder shown in `/memory` and compare it with the path where your earlier save actually wrote the file. Look for a missing `MEMORY.md` pointer, a different project directory, or a config mismatch before reaching for a third-party memory tool.

| Symptom | First check | Useful evidence |
|---|---|---|
| Save was reported, but no note is found | Actual write result and destination | File exists with the intended content |
| Note exists, but recall fails | Index, project scope, and available read records | Missing pointer, wrong path, or a read error |
| Correct note was read, but answer is wrong | Other instructions and the current question | Conflicting input or an unsupported conclusion |

### An edited or deleted note still appears

Ask Claude to retire the outdated value and update the saved preference, inspect every modified memory file on disk, and ask the same recall question in a fresh session. When our test replaced `OPAL-742` with `CEDAR-915`, `Write` calls updated both the topic file and `MEMORY.md`, and the next fresh call read the topic file and returned `CEDAR-915`.

For the removal check, we moved the test topic file outside the memory directory and deleted its pointer from `MEMORY.md`. The next fresh session answered `UNKNOWN`. Note that we edited the files manually on disk; this did not test a UI delete button or verify privacy erasure.

If an old value still shows up after updating memory, check the active conversation, your instruction files, and your prompt wording for another copy.

## Do you need a Claude Code memory plugin?

Stick with built-in memory if you just need Claude to retain a handful of project preferences and the save/recall check passes. Look for a plugin only when you hit a specific missing feature, such as searching across a large archive or reading notes from a different client. Before installing one, check what it records, where it stores data, and who can read it; our test did not compare plugins.

When a decision changes for the whole team, [Alook](https://alook.ai/) gives people and bots a shared channel to post the new decision alongside its source. Posting there coordinates the team, though it does not automatically sync into Claude Code's private auto-memory files; see [sharing context between agents](/blog/shared-context-between-agents).

When switching runtimes, pass the agreed decision and next verification step explicitly. Our guide on [keeping context across coding agent sessions](/blog/keep-context-across-coding-agent-sessions) covers how to structure those portable handoffs. Check how the next tool loads memory before expecting it to pick them up automatically.

## Claude Code memory FAQs

### Why does memory work in one project but not another?

Check where the note was actually saved on disk and compare it with the memory folder shown in the second project before editing the note. Our test used one Git project and one configuration directory; we did not test moving memory to another repository or machine.

### Should I add an index entry when recall fails?

Check MEMORY.md first. Our 2.1.304 run created its own index entry automatically, while an older 2.1.185 run in a custom directory needed a manual pointer before recall worked. Treat that manual edit as a fix for that specific setup, not a standard setup step.

### Which should I correct: memory or project instructions?

Update whichever file owns the rule. Standing project rules belong in your instruction files, while outdated preferences should be updated in auto memory. If both mention the old value, inspect both and repeat the fresh-session check. Adding another contradictory note leaves the conflict in place.

### Does compaction delete saved memory files?

Compaction trims conversation context, so a missing answer does not prove a saved file was deleted. Check the file on disk and confirm the session can still access it.

### Can subagents use the main session's auto memory?

Do not assume they inherit it. The [official subagent guide](https://code.claude.com/docs/en/sub-agents) describes separate memory configuration and context behavior; forks have different inheritance behavior. Check the agent type and version. For the broader distinction, see [Claude Code subagents and independent agents](/blog/claude-code-subagents-vs-independent-agents).
