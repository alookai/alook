## What does Claude Code remember between sessions?

A fresh conversation starts with a new context window.

| Carrier | What we use it for |
|---|---|
| Instruction files | Project rules maintained by the team |
| Auto memory | Notes Claude saves for future sessions |
| Session resume | The earlier conversation |

For our test, the team chose a separate session to check saved memory instead of resuming the earlier conversation.

Claude Code added direct `AGENTS.md` support in version 2.1.277. When a project already has a `CLAUDE.md`, Claude reads that by default. We check `/config` when a project relies on both formats.

## Where is Claude Code memory stored?

The default auto-memory directory is `~/.claude/projects/<project>/memory/`. `MEMORY.md` indexes the notes. Topic files hold details. `/memory` shows the active location and the auto-memory setting.

![Diagram comparing project instructions with auto memory. The index and topic note each contain the test label.](/blog/claude-code-memory/memory-files.webp)

A custom setup changes where to look, so we'd start with the location shown by `/memory` rather than a path copied from another machine.

## How do you check Claude Code memory across sessions?

We used a fictional review label for the test. A harmless fact keeps the result easy to distinguish from information already in the project.

For your own check, the same sequence works:

1. Ask Claude to save a harmless fact in auto memory, without changing project instruction files.
2. Open `/memory`, find the auto-memory folder, and inspect the note and its index.
3. Start a new conversation in the same project and ask for the fact without including the answer.

A correct answer shows recall. The session's read activity can show which note Claude opened. `/context all` lists the project instructions that loaded.

## What happened in our cross-session test?

The team ran the exercise on macOS with Claude Code 2.1.304 on October 21, 2026. The project was an empty Git repository with a separate configuration directory and default memory placement. Each CLI call started a new conversation. The [test record](https://alook.ai/blog/claude-code-memory/test-record.md) contains the selected tool events and answers.

The first save produced both a topic note and an index entry. The next conversation read the topic and returned `OPAL-742`. The index also contained that answer.

The team then changed the label to `CEDAR-915`, and a fresh conversation returned it. Finally, a team member moved the disposable topic outside the memory directory and removed its index entry. The next conversation answered `UNKNOWN`.

A test on Claude Code 2.1.185 with a custom memory directory gave us a different result: the topic existed but its index entry was missing, and the first recall failed. A manually added pointer made recall work. In the 2.1.304 default-placement run, Claude created the index entry itself. The index is the first file we'd inspect when a saved topic isn't found.

## Why isn't Claude Code memory working?

A failed save and a failed recall need different fixes. A reported save with no file points first to the write result and destination. For failed recall, we'd start with the index as in the test above, then check whether the note belongs to a different project directory.

### An old value keeps coming back

For the correction above, Claude updated both the topic note and its index. An old value can remain in the current conversation or a project instruction, so update that source when it owns the rule instead of adding a conflicting copy.

### Memory works in one project but not another

The default memory directory follows the Git repository. Its worktrees and subdirectories share that directory on the same machine. Outside Git, Claude uses the project root. Auto memory remains local to the machine. The active folder shown by `/memory` is the place to compare with the saved note.

## Do you need a Claude Code memory plugin?

For our label, the built-in notes were enough: the next session returned the saved value. We'd consider a plugin for a different job, such as searching a large archive or retrieving notes from another client. We'd first look at where it stores those records and who can access them.

By default, those notes stay on the machine and are scoped to the project. A teammate using another agent needs the decision shared with them. For our team, the conversation is where we leave that decision and its source. Our guide to [agent collaboration](https://alook.ai/blog/shared-context-between-agents) covers the handoff.

## Claude Code memory FAQs

### How much of MEMORY.md loads at startup?

Claude Code loads the first 200 lines or 25 KB of `MEMORY.md`, whichever limit comes first. Keep the index concise and move detail into topic files so the relevant pointers remain in the loaded portion.

### Does memory carry across machines?

Auto-memory files are not shared across machines or cloud environments.

### Does compaction delete saved memory files?

Compaction reduces conversation context. It doesn't delete the saved files on disk. Claude Code re-reads the project-root `CLAUDE.md` after compaction.

### Can subagents use the main session's auto memory?

The main conversation's auto memory isn't loaded into a non-fork subagent. A subagent can have its own persistent memory through its `memory` configuration. A fork inherits the parent conversation.
