Claude Code finishes a competitor pricing table on Monday. On Wednesday, Codex gets a vague prompt: “Look into competitor pricing.” It builds nearly the same table from scratch. Neither branch conflicts and no files overlap, yet you paid twice for the same output because the second session couldn't see what Monday's run already finished.

**To stop coding agents from duplicating work, assign one visible owner per goal, keep task status up to date, link finished and rejected work in new briefs, and check existing tasks before starting.** Git catches line-level merge conflicts, not two agents solving the same problem on separate branches.

Below are four common ways agents duplicate tasks and how to prevent them. If your agents are stepping on each other inside the same files, read [What Happens When Multiple AI Agents Edit the Same Repository?](/blog/multiple-ai-agents-edit-same-repository). Here we focus on the task layer: who owns this goal right now, and how does the next agent find out?

## Claim one owner so coding agents do not collide

Say you ask one agent to “implement rate limiting,” and another brief tells a second agent to “prevent API abuse.” Different words, same underlying job. Both start writing middleware. The same thing happens when you run Claude Code in one terminal and Codex in another without a shared claim on the outcome.

Backlogs without visible owners invite this kind of overlap. Anthropic ran into the same issue while building its multi-agent research system: two subagents researched semiconductor supply chains in parallel because their task boundaries were too loose. Their takeaway was simple: give every subagent a distinct objective, output format, and boundary ([Anthropic, 2025](https://www.anthropic.com/engineering/multi-agent-research-system)).

**Assign one owner to each goal before any agent makes its first tool call.** Once a task is claimed, any second agent joining in should review, extend, or take a clearly split subtask rather than rebuilding the whole thing.

You don't need heavy tooling for this. Issue assignees exist to make clear who owns an item ([GitHub Docs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/assigning-issues-and-pull-requests-to-other-github-users)), and a shared board or task file works just as well. Tag the bot name, runtime, session ID, or human owner so the next session sees the claim before starting.

## Point finished work so the next agent does not restart

Even after Monday's pricing table is done, a fresh prompt asking an agent to “research competitor pricing” without linking that table will usually trigger a full rebuild. Why would the new session know to look for it?

**If the next agent can't find finished work, it will redo it.** Close every completed task with a direct link to its output, whether that's a PR, report, decision note, or chat message. Then frame follow-up briefs as changes against that existing file:

> Start from Monday’s pricing comparison. Add the new annual plan and verify the enterprise limits. Do not rebuild the table.

That single link turns a blank-slate research task into a quick targeted update. If part of the earlier doc is outdated, name the stale section directly. [How to Keep Context Across Coding Agent Sessions](/blog/keep-context-across-coding-agent-sessions) walks through where to keep these links so they survive closed or compacted chats.

## Keep rejected approaches searchable for agents

Suppose your team reviews a write-through cache PR and rejects it because concurrent writes can clobber newer data. Two weeks later, another agent gets a prompt saying “add caching” and writes a clean write-through cache all over again. The code might look fine, yet the team already ruled that design out.

Shipped features leave code in the repo. Rejected ideas usually vanish inside old chat logs.

**Log rejected approaches right next to the goal, along with why they failed.** Two sentences are plenty:

> Rejected: write-through cache. Reason: concurrent writes can overwrite newer values. Revisit only if the write model changes.

Point future briefs at that note whenever they touch caching. If the system changes and the design becomes safe later, reopen the original record and note what changed instead of filing a brand-new ticket that buries the history. For wider practices on steering active agents, see [How to Run an AI Agent Team That Stays on Track](/blog/run-ai-agent-team-that-stays-on-track).

## Search the board before agents invent duplicates

Agent A writes a “billing summary” helper while Agent B builds an “invoice rollup” for the exact same page. Their ticket titles look different on the board, and Git merges both cleanly. You only spot the duplicate during code review.

**Check open, claimed, done, and rejected tasks by outcome, not just by title.** Concrete titles help here: “Show invoice totals on the billing screen” is much easier to spot in search than “Improve billing.”

When a matching task already exists, build on that thread or carve out only what's missing. Otherwise, claim the task and get started. Grepping the repo still helps you reuse existing helpers, while checking the task board first stops you from assigning a solved problem twice.

## Use a coding-agent handoff that prevents redo

![Hand-drawn checklist of five handoff fields that stop coding agents from redoing finished or rejected work](/blog/prevent-coding-agents-duplicating-work/handoff-five.webp)

A good handoff doesn't dump a full chat transcript on the next agent. Five short fields are enough to prevent repeat work:

1. **Goal and definition of done:** What concrete result counts as finished?
2. **Owner and status:** Who owns this right now, and is it open, active, done, or rejected?
3. **Existing artifacts:** Which PR, doc, report, or message already covers the completed parts?
4. **Do-not-redo notes:** Which approaches were ruled out, and why?
5. **Remaining gap:** What specific work is left?

That fifth line becomes the next agent's starting prompt. Leave it out, and the new session may treat the whole problem as greenfield again. [How agents keep decisions outside one chat](/blog/shared-context-between-agents) covers broader multi-agent handoffs; these five fields focus specifically on keeping ownership and past decisions intact.

Before spinning up another agent, ask yourself one question: **What will this run produce that we don't already have?** If you can't name it clearly, tighten the brief first.

## FAQ

**Why do coding agents duplicate work?**  
Coding agents duplicate work when separate briefs describe the same outcome and no shared record shows that the goal is already claimed, done, or rejected. Different wording can hide the overlap, especially when each agent only sees its own prompt.

**Is duplicate agent work a Git problem?**  
Usually no. Git catches overlapping edits to the same files, whereas duplicate tasks often land on clean, separate branches. You prevent that earlier with visible ownership, up-to-date status, and links to finished work.

**What should a coding-agent handoff include?**  
Include the goal, definition of done, current owner and status, links to existing outputs, rejected approaches with reasons, and the remaining gap. That lets the next agent see what to build without piecing together an earlier session.

**Does Alook automatically detect duplicate work?**  
No. Alook makes ownership and task history visible in shared rooms and messages, but it does not decide whether two briefs describe the same goal. A person or agent still needs to check existing work, claim the task, and resolve any overlap.
