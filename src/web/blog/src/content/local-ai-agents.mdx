## What is a local AI agent?

An AI agent pairs a model with a loop that reads state, calls tools, and checks what happened. A coding agent edits a repository and runs tests; a general work agent might read selected documents and draft a summary.

Take Claude Code: the CLI runs locally on your machine, while its standard setup [sends data over the network to interact with the LLM](https://code.claude.com/docs/en/data-usage). The agent process and file access can live on your computer while model requests still go to a hosted API.

## “Local” can describe three different layers

Model inference, tool execution, and shared coordination can each run in a different place.

### Local model and local runtime

Both model inference and the agent loop run on hardware you control. Running weights locally puts real demands on memory: model size, context window length, and concurrent requests all add up. A model that fits fine for a short chat can run tight on memory during a long, tool-heavy agent session.

### Local runtime with a hosted model

Here, the agent process runs next to your local files and calls an API for inference. Prompts and any file context sent with them leave the machine. This fits well when you want frontier-model capability on local repos without maintaining local inference hardware.

Our [OpenCode and Claude Code comparison](/blog/opencode-vs-claude-code) covers model choice and what changes when you switch between the two runtimes.

### Local runtime connected to a shared room

The agent runs on its owner’s machine while a shared service coordinates messages and channel state. Teammates can request work in the room, and the runtime keeps enforcing the file and tool permissions its owner configured.

When its host machine sleeps or loses connectivity, a local runtime goes offline too. If a task needs to run overnight, the machine running the loop matters just as much as the model you pick.

## What happened in our local file test

On November 17, 2026, we ran OpenCode 1.19.5 with Ollama 0.40.16 on a 16GB M1 Pro Mac, using the downloaded `qwen3.5:4b` model on Ollama’s MLX runner. We set a 65,536-token context window and restricted file reads to the test directory.

We created two short workshop notes. One listed the date as November 26 and room capacity as 24; the other said November 27 and 18. Both named the same invitation owner and a 14:00 start time. Without attaching the file contents to the prompt, we asked the agent to read the files, flag the conflicts, and leave the final decision to us.

On the first attempt, the agent requested paths at the filesystem root, outside the allowed directory. Direct `/tmp/...` paths were refused too; on this Mac, `/tmp` points to `/private/tmp`. For the next run, we used that `/private/tmp` canonical path and narrowed the permission rule to the test folder alone.

Before the successful comparison and its offline repeat, we turned off thinking and removed auto-loaded external skills. Two completed read calls then showed up in the tool log, each containing the actual file text. The agent caught both conflicts and named the invitation owner, yet left the shared 14:00 start time out of its summary of what matched.

Next, we blocked external network access for both OpenCode and Ollama while keeping loopback open for their local connection. Given the same prompt, the agent opened both files offline and missed the 14:00 start time the exact same way.

When we asked it to fetch `https://example.com` under that network block, the tool failed with a transport error. Rather than stopping there, the model suggested the page normally required authentication. Nothing in the tool output supported that claim, and fetching the page without the restriction returned HTTP 200 with no credentials. Checking the raw tool log let us separate the real connection error from the explanation the model invented.

Once the model and runtime were already downloaded, this setup compared local files without an internet connection. Any step that needs a live webpage adds a network dependency. Running a tiny file test first pays off because you can inspect every tool call and verify every claim in the answer by hand.

## How local AI agents fit into a team

When a teammate needs to review an agent's output, share the concrete artifact and the open question you want checked. For our workshop notes, that means passing along the conflicting dates and room capacities rather than just saying the summary is done, while keeping credentials and unrelated local files off the thread.

## Local AI agent FAQs

### Do local AI agents work offline?

A local model and runtime can complete tasks whose inputs and tools are available on the machine. Our two-file task continued with external networking blocked; the web fetch did not. Downloading the model and preparing the runtime were separate, online steps.

### Does a local agent require a local LLM?

No. Claude Code’s standard setup is one example of a local runtime using hosted inference. A local LLM is a model choice; it is separate from where file reads and commands run.

### Are local AI agents private?

Local inference keeps model requests on your hardware, though tools, logs, telemetry, and shared messages can still send data elsewhere. Checking all three layers lets you trace what a specific task sends out instead of putting one blanket privacy label on the whole tool.

### Can teammates use the same local agent?

A shared conversation lets teammates request work and review what an agent returns. It doesn’t expand the runtime’s local permissions. Keep the folder and tool scope with the owner who runs it.
